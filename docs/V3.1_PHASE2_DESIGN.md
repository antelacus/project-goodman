## 1. 设计目标

### 1.1 核心目标

将当前代码库重构为**可扩展的工作流系统**，为未来会计流程的各个模块提供统一基础设施。

**关键理念**:

- 当前的三个功能模块（财务分析、合规指导、首页对话）是**起点**，不是终点
- 架构需支持未来添加更多会计流程模块（记账分录、对账、结账、报表生成等）
- 为 V3.4 LangGraph 迁移做准备，但保持架构的通用性

### 1.2 非目标

- ❌ 不改变现有 API 行为（100% 向后兼容）
- ❌ 不添加新功能
- ❌ 不引入 LangGraph 依赖（留给 V3.4）

## 2. 架构设计

### 2.1 当前架构问题

```
当前: 每个 API 路由都是独立的"单体"
├── financial-analysis/route.ts  (661 行)
├── guidance-chat/route.ts       (907 行)
└── landing-chat/route.ts        (224 行)

问题:
- 类型定义重复（每个路由重新定义相同类型）
- 工具分散（preset-functions, structured-extraction 等无统一接口）
- 工作流逻辑隐藏在路由代码中（难以复用、测试、调试）
- 无法扩展到新模块（每次都要重写类似逻辑）
```

### 2.2 目标架构

```
通用工作流基础设施
├── 核心引擎层
│   ├── WorkflowEngine         # 通用状态机执行器
│   ├── ToolRegistry           # 统一工具注册表
│   └── ErrorHandler           # 统一错误处理
├── 类型系统层
│   ├── WorkflowState (模板)   # 所有工作流遵循的状态模式
│   ├── Tool (接口)            # 统一工具接口
│   └── WorkflowError (层次)   # 结构化错误类型
└── 工作流模块层（可插拔）
    ├── financial-analysis/    # 当前: 财务分析
    ├── guidance-chat/         # 当前: 合规指导
    ├── landing-chat/          # 当前: 首页对话
    ├── journal-entry/         # 未来: 记账分录
    ├── reconciliation/        # 未来: 对账
    ├── closing/               # 未来: 结账
    └── reporting/             # 未来: 报表生成

特点:
✅ 新模块复用核心基础设施
✅ 步骤函数独立可测试
✅ 工作流可视化为状态图
✅ 与 LangGraph StateGraph 概念对齐
```

### 2.3 架构分层

| 层级 | 职责 | 文件位置 |
|------|------|----------|
| **API 路由层** | 解析请求、调用工作流、格式化响应 | `src/app/api/*/route.ts` |
| **工作流编排层** | 执行步骤序列、管理状态流转 | `src/lib/workflows/*/index.ts` |
| **步骤函数层** | 独立业务逻辑单元 | `src/lib/workflows/*/steps.ts` |
| **工具与工具层** | 可复用操作（计算、搜索、提取） | `src/lib/tools/*` |
| **外部服务层** | OpenAI、Supabase、Storage | 现有不变 |

## 3. 五阶段重构设计

### 3.1 Phase A: 提取显式状态类型

**目标**: 为所有工作流创建统一的状态类型模式

**设计**: 通用状态模板

```typescript
// src/lib/types/workflow-states.ts

// 通用状态模板（所有工作流遵循）
interface WorkflowState {
  input: unknown;              // 来自 API 请求
  [stepName: string]: unknown; // 各步骤的中间状态
  output: unknown;             // 返回给 API 响应
  meta: WorkflowMeta;          // 工作流元数据
}

interface WorkflowMeta {
  startTime: number;
  endTime?: number;
  currentStep: string;
  errors: WorkflowError[];
  debugInfo?: Record<string, unknown>;
}

// 具体工作流状态示例
interface FinancialAnalysisState extends WorkflowState {
  input: { question: string; documentId?: string };
  routing: { selectedFunction: string | null; confidence: number };
  dataQuery: { queryResults: Record<string, number>; missingMetrics: string[] };
  calculation: { result: number | null; formula: string };
  confidence: { score: number; passed: boolean };
  output: { answer: string; calculation?: CalculationResult };
}
```

**关键设计决策**:

- 使用 TypeScript 接口继承保证所有状态遵循统一模式
- `meta` 字段统一追踪工作流执行信息
- 未来新模块只需定义自己的步骤状态，继承 `WorkflowState`

**文件结构**:

```
src/lib/types/
├── index.ts                  # 统一导出
├── workflow-states.ts        # 工作流状态模板 + 具体状态
├── tool-types.ts             # 工具接口
├── api-types.ts              # API 请求/响应
└── domain-types.ts           # 业务领域类型
```

### 3.2 Phase B: 提取步骤函数

**目标**: 将路由中的隐式步骤提取为可复用的纯函数

**设计**: 步骤函数契约

```typescript
// 步骤函数签名: 接收状态，返回更新后的状态
type StepFunction<S extends WorkflowState> = (state: S) => Promise<S>;

// 示例: 财务分析工作流的步骤
// src/lib/workflows/financial-analysis/steps.ts

export const routeToFunction: StepFunction<FinancialAnalysisState> = async (state) => {
  // 调用 OpenAI 选择函数
  const selectedFunction = await selectFunction(state.input.question);
  return { ...state, routing: { selectedFunction, confidence: 0.85 } };
};

export const queryData: StepFunction<FinancialAnalysisState> = async (state) => {
  // 查询数据库
  const results = await fetchMetrics(state.routing.selectedFunction);
  return { ...state, dataQuery: results };
};

export const calculate: StepFunction<FinancialAnalysisState> = async (state) => {
  // 执行计算
  const result = await executeCalculation(state.dataQuery.queryResults);
  return { ...state, calculation: result };
};
```

**工作流编排器**:

```typescript
// src/lib/workflows/financial-analysis/index.ts

export async function runFinancialAnalysisWorkflow(
  input: FinancialAnalysisState['input']
): Promise<FinancialAnalysisState> {
  let state = initializeState(input);

  // 顺序执行步骤
  state = await steps.routeToFunction(state);
  state = await steps.queryData(state);
  state = await steps.calculate(state);
  state = await steps.evaluateConfidence(state);
  state = await steps.generateResponse(state);

  return state;
}
```

**路由简化**（从 661 行 → ~30 行）:

```typescript
// src/app/api/financial-analysis/route.ts

export async function POST(request: Request) {
  const body = await request.json();
  const state = await runFinancialAnalysisWorkflow(body);
  return Response.json(state.output);
}
```

**文件结构**:

```
src/lib/workflows/
├── financial-analysis/
│   ├── steps.ts      # 5-7 个步骤函数
│   └── index.ts      # 工作流编排器
├── guidance-chat/
│   ├── steps.ts
│   └── index.ts
├── landing-chat/
│   ├── steps.ts
│   └── index.ts
└── shared/
    ├── confidence.ts  # 共享的置信度计算步骤
    └── validation.ts  # 共享的输入验证步骤
```

### 3.3 Phase C: 集中工具定义

**目标**: 创建统一的工具接口和注册表

**设计**: 工具抽象层

```typescript
// src/lib/tools/types.ts

interface Tool<TInput = unknown, TOutput = unknown> {
  name: string;
  description: string;
  category: 'financial' | 'search' | 'extraction' | 'storage';

  inputSchema: z.ZodSchema<TInput>;   // 输入验证
  outputSchema: z.ZodSchema<TOutput>; // 输出验证

  execute: (input: TInput) => Promise<TOutput>;

  metadata?: {
    requiredInputs?: string[];  // 财务函数需要的指标
    timeout?: number;
    retryable?: boolean;
  };
}
```

**工具注册表**:

```typescript
// src/lib/tools/registry.ts

class ToolRegistry {
  private tools = new Map<string, Tool>();

  register(tool: Tool): void { /* ... */ }
  get(name: string): Tool | undefined { /* ... */ }
  getByCategory(category: string): Tool[] { /* ... */ }

  // 转换为 OpenAI function definitions
  toOpenAIFunctionDefs(): ChatCompletionTool[] { /* ... */ }

  // 执行工具（带验证和错误处理）
  async execute<T>(name: string, input: unknown): Promise<T> { /* ... */ }
}

export const toolRegistry = new ToolRegistry();
```

**注册现有工具**:

```typescript
// src/lib/tools/financial-tools.ts

// 将 preset-functions 注册为工具
presetFunctions.forEach(fn => {
  toolRegistry.register({
    name: fn.name,
    description: fn.interpretation,
    category: 'financial',
    inputSchema: z.object({ /* 动态生成 */ }),
    outputSchema: z.object({ value: z.number(), formula: z.string() }),
    execute: async (input) => fn.calculate(input),
    metadata: { requiredInputs: fn.requiredInputs },
  });
});
```

**关键设计决策**:

- 保留 `preset-functions.ts` 不变（向后兼容）
- 工具注册在应用启动时完成
- 步骤函数通过 `toolRegistry.execute()` 调用工具
- 为 LangGraph `ToolNode` 迁移预留接口

### 3.5 Phase E: 创建错误类型层次

**目标**: 结构化错误处理，为 LangGraph 条件边做准备

**设计**: 错误基类

```typescript
// src/lib/errors/base.ts

abstract class WorkflowError extends Error {
  abstract readonly code: string;
  abstract readonly recoverable: boolean; // 是否可重试

  toJSON() { /* 序列化为 API 响应 */ }
}
```

**错误分类**:

```typescript
// 工具错误
class ToolExecutionError extends WorkflowError {
  code = 'TOOL_EXECUTION_ERROR';
  recoverable = true; // 可以尝试其他工具
}

// 工作流错误
class InsufficientDataError extends WorkflowError {
  code = 'INSUFFICIENT_DATA';
  recoverable = true; // 可以尝试其他数据源
}

class LowConfidenceError extends WorkflowError {
  code = 'LOW_CONFIDENCE';
  recoverable = true; // 可以请求用户确认
}
```

**使用示例**:

```typescript
// 步骤函数中抛出错误
export const queryData: StepFunction<State> = async (state) => {
  const results = await fetchData();

  if (results.missing.length > 0) {
    throw new InsufficientDataError(results.missing);
  }

  return { ...state, data: results };
};

// 工作流编排器处理错误
try {
  state = await steps.queryData(state);
} catch (error) {
  if (error.recoverable) {
    // 尝试备用策略
    state = await steps.tryAlternativeSource(state);
  } else {
    throw error; // 不可恢复，返回错误响应
  }
}
```

## 5. LangGraph 对齐

### 5.1 概念映射

| V3.1 组件 | LangGraph 概念 | 迁移工作量 |
|-----------|----------------|------------|
| `WorkflowState` | `StateGraph<State>` 类型参数 | 直接使用 |
| 步骤函数 | Graph `Node` 函数 | 包装为节点 |
| `ToolRegistry` | `ToolNode` | 转换接口 |
| Error `recoverable` | 条件边路由逻辑 | 映射到边 |
| 工作流编排器 | `StateGraph.compile()` | 替换为图定义 |

### 5.2 迁移预览

**V3.1 代码（重构后）**:

```typescript
export async function runWorkflow(input) {
  let state = init(input);
  state = await step1(state);
  state = await step2(state);
  return state;
}
```

**V3.4 代码（LangGraph）**:

```typescript
import { StateGraph } from '@langchain/langgraph';

const workflow = new StateGraph<State>()
  .addNode('step1', step1)  // 复用 V3.1 的步骤函数！
  .addNode('step2', step2)
  .addEdge('step1', 'step2');

const app = workflow.compile();
const result = await app.invoke(input);
```

**估算**: 每个工作流 2-3 天迁移（主要是图定义，步骤函数几乎不改）

## 7. 架构决策记录

### 7.1 已解决问题

| 问题 | 决策 | 理由 |
|------|------|------|
| 错误处理策略 | 错误冒泡到工作流层 | 符合 LangGraph 条件边模式 |
| 状态持久化 | V3.1 使用内存，V3.4 添加 Redis | 渐进式添加复杂度 |
| 工具注册时机 | 应用启动时注册 | 简单，所有工具立即可用 |
| 工作流 API | 暴露 `.run(input)` | V3.1 简单，V3.4 迁移到 `.compile()` |
| 步骤函数依赖 | 闭包依赖注入 | 灵活，易于测试 |

### 7.2 设计原则

1. **模块化优先**: 每个工作流是独立模块，可插拔
2. **通用基础设施**: 核心组件（状态、工具、错误）对所有模块可用
3. **渐进式迁移**: 可以逐个模块迁移，不需一次性完成
4. **向后兼容**: API 行为不变，旧代码可回退
5. **面向未来**: 架构对齐 LangGraph，为 V3.4 迁移铺路
