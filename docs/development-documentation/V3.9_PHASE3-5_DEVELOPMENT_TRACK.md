## 2. Batch 1: 安全紧急修复

### 2.1 REQ-001: CSP 修复

**问题**: CSP 配置使用 `'unsafe-inline'` 和 `'unsafe-eval'`，XSS 防护被削弱。

**解决方案**: 移除 `'unsafe-eval'`，保留 `'unsafe-inline'`（Next.js hydration 需要）。

**变更文件**: `next.config.ts`

```typescript
// Before
"script-src 'self' 'unsafe-inline' 'unsafe-eval'"

// After
"script-src 'self' 'unsafe-inline'"
```

**说明**: `'unsafe-eval'` 允许 `eval()` 等动态代码执行，是重大 XSS 风险。Next.js 15 生产构建不需要 `eval()`。

---

### 2.2 REQ-002: 移除客户端敏感数据

**问题**: 敏感数据存储在 localStorage/sessionStorage。

**解决方案**:
1. 移除 `PasswordModal.tsx` 中的 localStorage 会话存储
2. 移除 `documents/page.tsx` 中的 sessionStorage 密码获取
3. 更新 `/api/documents` PATCH 端点使用 session-based 认证

**变更文件**:
- `src/components/admin/PasswordModal.tsx` - 移除 localStorage，改用 API 检查会话
- `src/components/admin/index.ts` - 更新导出


### 2.3 REQ-003: 内存 Map 架构说明

**问题**: Rate limiter 使用内存 Map，设计文档建议迁移到 Redis。

**分析结果**:
- Rate limiter 运行在 Next.js Edge Runtime (middleware)
- Edge Runtime 不支持 Node.js 模块如 `ioredis`
- 对于单 VPS 部署，内存 Map 是可接受的方案

**解决方案**: 添加架构说明文档，明确设计决策。

**变更文件**: `src/lib/security/rate-limiter.ts`

```typescript
/**
 * ARCHITECTURE NOTE (V3.9):
 * Uses in-memory Map because this runs in Next.js Edge Runtime (middleware).
 * Edge Runtime doesn't support Node.js modules like ioredis.
 *
 * For single-VPS deployment (current architecture): In-memory is acceptable.
 * For distributed/multi-instance deployment: Consider:
 *   1. Use Upstash Redis (Edge-compatible, fetch-based client)
 *   2. Move rate limiting to API routes with Node.js runtime
 */
```

### 2.5 REQ-012b: Service Role 隔离

**问题**: 使用 Service Role Key 的模块可能被意外导入到客户端代码。

**解决方案**: 添加文件级警告和运行时检查。

**变更文件**: `src/lib/documents/storage.ts`

```typescript
/**
 * ⚠️ SERVER-SIDE ONLY ⚠️
 * This module uses SUPABASE_SERVICE_ROLE_KEY and must NEVER be imported
 * in Client Components.
 */

// Runtime check to prevent accidental client-side import
if (typeof window !== 'undefined') {
  throw new Error(
    '[SECURITY] storage.ts must not be imported in client-side code.'
  );
}
```

## 5. Batch 1 补丁: 客户端导入修复

### 5.1 问题描述

**症状**: Guest 用户访问 `/documents` 页面时出现客户端异常错误。

**根本原因**: REQ-012b 在 `storage.ts` 添加的运行时检查：

```typescript
if (typeof window !== 'undefined') {
  throw new Error('[SECURITY] storage.ts must not be imported in client-side code.');
}
```

`documents/page.tsx` 通过 `@/lib/documents` 导入 `isImage`, `isPdf`, `isExcel` 工具函数，这些函数从 `storage.ts` 重导出，导致整个 storage 模块被加载，触发运行时错误。

### 5.2 解决方案

将纯工具函数分离到客户端安全的独立文件：

**新增文件**: `src/lib/documents/file-utils.ts`

```typescript
// 客户端安全的文件类型检测函数
export function getFileExtension(filename: string): string
export function isPreviewable(filename: string): boolean
export function isImage(filename: string): boolean
export function isPdf(filename: string): boolean
export function isExcel(filename: string): boolean
```

**变更文件**:

| 文件 | 变更 |
|------|------|
| `src/lib/documents/file-utils.ts` | **新增** - 客户端安全的工具函数 |
| `src/lib/documents/storage.ts` | 从 file-utils.ts 导入并重导出（向后兼容） |
| `src/lib/documents/index.ts` | 文件工具从 file-utils.ts 导出，存储函数从 storage.ts 导出 |

### 5.3 架构变更

```
Before:
  documents/page.tsx → @/lib/documents → storage.ts (throws error)

After:
  documents/page.tsx → @/lib/documents → file-utils.ts (client-safe)
  api/routes → @/lib/documents → storage.ts (server-only)
```

### 6.2 REQ-005: 消息转换修复

**问题**: LangChain 消息转换为 OpenAI 格式时丢失 `tool_call_id` 和 `tool_calls`。

**解决方案**: 新增 `convertToOpenAIMessages()` 函数，正确处理三种消息类型：

```typescript
function convertToOpenAIMessages(messages: BaseMessage[]): OpenAI.Chat.ChatCompletionMessageParam[] {
    return messages.map(msg => {
        if (msgType === "human") → { role: "user", content }
        if (msgType === "ai")    → { role: "assistant", content, tool_calls? }
        if (msgType === "tool")  → { role: "tool", tool_call_id, content }
    });
}
```

**变更文件**: `src/lib/workflows/core/nodes/agent-loop.ts`

### 6.3 REQ-006: JSON.parse 错误处理

**问题**: `JSON.parse(tc.function.arguments)` 可能抛出异常。

**解决方案**: 新增 `parseToolArguments()` 安全解析函数：

```typescript
function parseToolArguments(argsString: string, toolName: string): Record<string, unknown> {
    try {
        return JSON.parse(argsString);
    } catch (e) {
        console.warn(`[agent-loop] Failed to parse arguments for tool "${toolName}": ${e}`);
        return {};
    }
}
```

**变更文件**: `src/lib/workflows/core/nodes/agent-loop.ts`

### 6.4 REQ-013: State Reducer 评估

**问题**: 设计文档建议将 reducer 从简单替换改为合并语义。

**评估结果**: 当前实现正确，无需修改。

**原因**:
- `agent.messages` 是 `agent` 对象的嵌套属性，不是独立 channel
- 所有节点返回完整状态对象（如 `{ agent: { ...agent, messages: newMessages } }`）
- `toolExecutorNode` 已在返回值中构建完整数组
- 简单替换语义配合完整状态返回是正确的模式

### 7.2 REQ-004: 临时文档清理函数修复

**问题**: `cleanup_temp_documents()` 函数引用不存在的 `is_temp` 字段。

**背景分析**:
- 原始设计（早期迁移）使用 `is_temp = true` 标识临时文档
- V3.10 引入了更完善的所有权模型：`owner_type` 和 `expires_at`
- 但清理函数未更新以使用新字段

**解决方案**: 更新清理函数使用 V3.10 所有权模型：

```sql
-- Before (broken)
DELETE FROM documents WHERE is_temp = true AND created_at < NOW() - INTERVAL '24 hours'

-- After (fixed)
DELETE FROM documents
WHERE owner_type = 'guest'
  AND expires_at IS NOT NULL
  AND expires_at < NOW()
```

**新增文件**: `supabase/migrations/20251231000000_fix_temp_cleanup_function.sql`

**部署步骤**:
1. ✅ 迁移文件已创建
2. ⏳ 需手动在 Supabase Dashboard → SQL Editor 执行迁移

| 空字符串内容处理 | `agent-loop.ts` | 使用 `typeof` 检查替代 truthy 检查 |

### 8.3 REQ-005 补充: Tool Calls 格式转换

**问题**: Batch 2 的 REQ-005 修复了消息转换函数，但未处理 AIMessage 创建时的格式问题。

**根本原因**:
```typescript
// agent-loop.ts 原代码
const aiMessage = new AIMessage({
    content: message.content || "",
    tool_calls: message.tool_calls as any,  // 直接存储 OpenAI 格式
});
```

OpenAI 返回格式: `{ id, type, function: { name, arguments } }`
LangChain 期望格式: `{ id, name, args }`

**解决方案**: 在创建 AIMessage 时转换格式。

### 8.4 消息历史加载修复

**问题**: `load-memory.ts` 从数据库加载消息时，只恢复了 `content`，未恢复 `tool_calls` 和 `tool_call_id`。

**影响**: 连续提问时，历史中的工具调用消息不完整，导致 OpenAI API 报错。

**解决方案**: 完整恢复 AIMessage 的 `tool_calls` 和 ToolMessage 的 `tool_call_id`。

### 8.5 空字符串内容处理

**问题**: `convertToOpenAIMessages` 中使用 `content || null`，空字符串被转换为 `null`。

**影响**: 工具调用消息的 content 通常为空字符串，转换为 `null` 后 OpenAI 报错。

**解决方案**: 使用 `typeof content === "string"` 检查。

### 8.6 Storage 模块客户端导入

**问题**: Batch 1 补丁创建了 `file-utils.ts`，但 barrel export 仍导出 storage 函数，导致客户端加载时触发安全检查。

**解决方案**: 从 `index.ts` 移除 storage 导出，更新 5 个 API 路由使用直接导入。
