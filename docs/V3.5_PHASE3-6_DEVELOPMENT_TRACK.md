## 概述

V3.5 将 V3.4 的线性 LangGraph 工作流升级为具备 Agent 能力的循环工作流。核心升级包括：

1. **图级别 Agent 循环**: Agent ⇄ Tool 循环从节点内部提升到 StateGraph 层面
2. **对话记忆系统**: 基于 Supabase PostgreSQL 的会话持久化
3. **多工具顺序调用**: 支持单次请求内多个工具依次执行

**相关文档**:

- 需求文档: `docs/V3.5_PHASE1_REQUIREMENT_DECLARATION.md`
- 设计文档: `docs/V3.5_PHASE2_DESIGN.md`

## Phase A: 数据库迁移 + Memory 服务 ✅

**完成日期**: 2025-12-22

### A1: 数据库迁移 ✅

**文件**: `supabase/migrations/20251222_conversation_memory.sql`

创建表结构:

- `conversation_sessions`: 会话表 (id, workflow_type, metadata, timestamps)
- `conversation_messages`: 消息表 (id, session_id, role, content, tool_calls, sequence_number)

索引:

- `idx_messages_session`: 按 session_id 查询消息
- `idx_sessions_workflow_type`: 按 workflow_type 筛选会话

RLS 策略:

- 暂时开放所有访问（无用户系统）
- 为 V3.8 用户系统预留 user_id 字段

### A2: ConversationMemory 服务 ✅

**文件**: `src/lib/memory/conversation-memory.ts`

核心功能:

- `createSession(workflowType, metadata)`: 创建新会话
- `loadSession(sessionId, limit)`: 加载会话历史（默认 50 条）
- `saveMessages(sessionId, messages)`: 保存新消息
- `getOrCreateSession(sessionId, workflowType)`: 获取或创建会话

设计要点:

- 消息按 `sequence_number` 排序
- 自动更新会话 `updated_at` 时间戳
- 支持 tool_calls 和 tool_call_id 字段


### B2: Agent 节点实现 ✅

**文件**: `src/lib/workflows/financial-analysis/nodes.ts`

节点列表:

| 节点 | 职责 |
|------|------|
| `loadMemoryNode` | 从数据库加载历史消息 |
| `agentNode` | LLM 思考，决定调用工具或完成 |
| `toolNode` | 执行待处理的工具调用 |
| `generateResponseNode` | 生成最终用户响应 |
| `saveMemoryNode` | 保存对话到数据库 |

### B3: Agent 图构建 ✅

**文件**: `src/lib/workflows/financial-analysis/graph.ts`

图结构:

```
START → loadMemory → agentNode ⇄ toolNode → generateResponse → saveMemory → END
```

条件边:

- `afterAgentNode`: 根据 isComplete / pendingToolCalls / maxIterations 决定下一步
- `afterToolNode`: 始终返回 agentNode

### B4: API Route 更新 ✅

**文件**: `src/app/api/financial-analysis/route.ts`

变更:

- 请求支持 `sessionId` 参数
- 响应包含 `sessionId` 字段
- 使用 `runFinancialAgentWorkflow` 替代旧工作流

## 关键设计决策

### 1. Session ID 生命周期

**决策**: 后端生成，首次响应返回，前端需存储并传回

**原因**: 确保 UUID 唯一性，前端无需依赖外部库

### 2. 最大迭代次数

**决策**: 默认 5 次（从设计文档的 10 次调整）

**原因**: 平衡功能与成本/延迟

- 典型场景: 2-3 次循环
- 复杂场景: 4-5 次循环
- 最大延迟: ~25-30 秒

### 3. 工具执行方式

**决策**: 顺序执行（非并行）

**原因**: 稳定可靠，V3.6 再考虑并行优化

### 4. 消息限制

**决策**: 默认加载最近 50 条消息

**原因**: 防止 token 超限，保留足够上下文
