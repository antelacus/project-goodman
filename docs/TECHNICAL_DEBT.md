### TD-003: Agent 可观测性缺口

**领域**: 可观测性

**问题**:
LangGraph Agent 工作流没有 LangSmith 或同类追踪工具。复杂 Agent 行为的调试依赖控制台日志。

**影响**:

- 难以调试生产环境的 Agent 问题
- 无法看到每步的 Token 使用量
- 无 Agent 工作流的性能分析

**建议解决方案**:
集成 LangSmith 用于：

- 追踪可视化
- Token 使用量跟踪
- 性能指标

**工作量估计**: 中

**状态**: 延迟到 V5+ - 当前日志对单人开发足够

### TD-004: 手动部署

**领域**: 基础设施

**问题**:
通过 `docker compose up -d --build` 手动部署。没有 CI/CD 流水线，推送时没有自动化测试。

**影响**:

- 部署时有人为错误风险
- 没有自动回滚能力
- 没有部署前测试关卡

**建议解决方案**:
GitHub Actions CI/CD 流水线，包含以下阶段：

**阶段 1: 代码质量检查** (每次 push 到 development)
```yaml
- npm ci                    # 安装依赖
- npm run lint              # ESLint 检查
- npm run test              # Vitest 单元测试
- npx tsc --noEmit          # TypeScript 类型检查
```

**阶段 2: 安全检查** (每次 push 到 development)
```yaml
- npm audit --audit-level=high    # 依赖漏洞扫描
# 高危漏洞会阻止流水线，中/低危仅警告
```

**阶段 3: 构建验证** (每次 push 到 development)
```yaml
- npm run build             # Next.js 生产构建
- docker build .            # Docker 镜像构建测试
```

**阶段 4: 部署** (仅 main 分支合并后)
```yaml
- SSH 到生产服务器
- docker compose pull
- docker compose up -d
- curl /api/health 验证部署成功
```

**触发规则**:

| 事件 | 运行阶段 |
|------|----------|
| Push to `development` | 阶段 1-3（检查 + 构建） |
| PR to `main` | 阶段 1-3（检查 + 构建） |
| Merge to `main` | 阶段 1-4（检查 + 构建 + 部署） |

**所需 Secrets**:

| Secret | 用途 |
|--------|------|
| `DEPLOY_HOST` | 生产服务器 IP |
| `DEPLOY_USER` | SSH 用户名 |
| `DEPLOY_KEY` | SSH 私钥 |
| `SUPABASE_PROJECT_ID` | 类型生成（可选） |

**工作量估计**: 中

**状态**: 计划实施 - CI/CD 将整合 npm audit 等自动化检查

### TD-014: expr-eval 依赖漏洞

**领域**: 安全

**问题**:
`expr-eval` 库有两个高危漏洞：

- GHSA-8gw3-rxh4-v6jx: 原型污染
- GHSA-jc85-fpwf-qm7x: 未限制传递给 evaluate 函数的函数

无可用修复版本。

**影响**:

- 理论上可能被恶意输入利用
- npm audit 报告持续显示漏洞

**当前缓解措施**:

- 仅处理管理员定义的财务公式
- 用户输入在到达 expr-eval 之前已验证
- 不暴露给任意用户输入

**建议解决方案**:

- 评估替代库（如 mathjs）
- 或实现自定义安全表达式解析器

**工作量估计**: 大

**状态**: 延迟到 V5+ - 当前缓解措施可接受

### TD-017: API 路由 Zod 验证覆盖不完整

**领域**: 代码质量

**问题**:
部分 API 路由使用内联验证而非 Zod schema：
- `/api/quick-actions/extract` - 内联文件类型/大小检查
- `/api/documents/upload-temp` - TypeScript 接口但无运行时验证
- `/api/chat/route.ts` - 简单 `if (!message)` 检查

**影响**:

- 错误消息格式不一致
- 验证逻辑分散，难以维护
- 缺少类型推断的好处

**当前缓解措施**:

- 关键路由（chat/stream、auth、reports）已使用 Zod
- 内联验证功能上可用，只是不够优雅
- 无安全风险，仅为代码质量问题

**建议解决方案**:

- 为所有 POST/PATCH 路由添加 Zod schema
- 统一到 `src/lib/validation/api-schemas.ts`

**工作量估计**: 小

**状态**: 延迟到 V5+ - 低优先级代码质量改进

## 开发注意事项

> 环境配置和预期行为，非债务项。

- **Redis**: Docker 中通过 `goodman-redis` 主机名连接；启动时连接错误是预期的，应用会自动重试
- **环境变量**: `.env` 中包含 `$` 字符的变量需要转义
- **Docker**: 仅用于生产环境；本地开发使用 `npm run dev`
- **Supabase**: `.temp/` 目录已 gitignore，会自动重新生成
