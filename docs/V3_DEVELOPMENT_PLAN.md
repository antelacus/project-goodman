## V3 版本路线图

### 战略方向：AI 辅助系统 → 财务 AI Agent

V3 代表了从"AI 辅助"系统到"AI Agent"架构的根本性转变：

| 方面         | V2（当前）        | V3（目标）           |
| ------------ | ----------------- | -------------------- |
| **用户交互** | 用户选择功能/文档 | Agent 决定使用什么   |
| **工具执行** | 每次请求单个工具  | 带推理的多工具链     |
| **错误处理** | 向用户返回错误    | Agent 用不同方法重试 |
| **状态管理** | 无状态请求        | 有记忆的有状态 Agent |
| **响应时间** | 10-30 秒          | 复杂任务可达数分钟   |

### 实现阶段

| 阶段     | 功能               | 前置条件   | 状态 |
| -------- | ------------------ | ---------- | ---- |
| **V3.0** | VPS 迁移           | 无         | ✅ 完成 (2025-12-12) |

| **V3.5** | 财务 Agent 逻辑升级 | V3.4       | ✅ 完成 (2025-12-23) |

### 架构演进

```
V2 架构（当前）
─────────────────────────
用户 → API Route → LLM (单次调用) → 响应
        └── 手动工具选择
        └── 60s 超时限制
        └── 请求间无状态

V3 架构（目标）
─────────────────────────
用户 → Agent Controller → StateGraph
                              ├── 意图分析节点
                              ├── 文档发现节点
                              ├── 工具选择节点
                              ├── 执行节点（带重试）
                              ├── 验证节点
                              └── 响应生成节点
        └── WebSocket 流式传输状态
        └── 无超时限制
        └── 对话记忆
        └── 后台处理
```

## 1. [V3.0] VPS 迁移

### 概述

从 Vercel（免费层）迁移到 VPS，以更好地控制计算资源，特别是对于需要长时间运行进程和实时通信的 AI Agent 架构。

### 动机

- **AI Agent 架构**：多步骤推理需要比 serverless 允许的更长执行时间
- **无超时限制**：Agent 可以根据需要推理数分钟
- **WebSocket 支持**：实时向 UI 推送 Agent "思考"步骤
- **后台工作进程**：预处理文档、预热缓存、运行定时任务
- **持久连接**：保持数据库/OpenAI 连接活跃以提高性能

### 当前 Vercel 限制

| 限制           | Hobby 层      | 对 AI Agent 的影响              |
| -------------- | ------------- | ------------------------------- |
| **函数超时**   | 最大 60s      | ⚠️ **关键阻碍**：复杂 Agent 链  |
| **WebSockets** | ❌ 不支持     | ❌ **阻碍**：实时 Agent 状态    |
| **后台任务**   | ❌ 不支持     | ❌ **阻碍**：文档预处理         |

### VPS vs Vercel 对比

| 能力             | Vercel (Serverless) | VPS (持久服务器)           |
| ---------------- | ------------------- | -------------------------- |
| 执行超时         | 最大 60s            | **无限制**                 |
| 后台任务         | ❌ 不支持           | ✅ Cron、工作进程、队列    |
| WebSocket        | ❌ 不支持           | ✅ 完全支持                |
| 请求间状态       | 无状态              | ✅ 内存缓存                |
| 长时间运行进程   | ❌ 不支持           | ✅ Agent 循环、批处理      |

### 可用 VPS 资源 (RackNerd)

| 资源       | 规格                 |
| ---------- | -------------------- |
| **内存**   | 4 GB                 |
| **磁盘**   | 65 GB SSD            |
| **操作系统** | Ubuntu 24.04 LTS   |
| **IP**     | 104.168.38.213       |

### 迁移范围

**保持不变**：

- Supabase (PostgreSQL + pgvector) - 已是外部服务
- Supabase Storage - 已是外部服务
- OpenAI API - 已是外部服务
- 所有应用代码 - 无需修改

**需要变更**：

- 托管平台 (Vercel → VPS)
- 进程管理 (serverless → PM2)
- 反向代理 (Vercel Edge → nginx)
- SSL (Vercel 自动 → Let's Encrypt)

### 目标架构

```
┌─────────────────────────────────────────────────────────┐
│              VPS (104.168.38.213)                       │
├─────────────────────────────────────────────────────────┤
│  nginx (反向代理 + SSL + WebSocket 支持)                 │
│    ↓                                                    │
│  PM2 (进程管理器，自动重启，日志)                         │
│    ├── Next.js App (端口 3000)                          │
│    └── Agent Worker (可选, 端口 3001)                   │
├─────────────────────────────────────────────────────────┤
│  仍保持云托管：Supabase, OpenAI API                      │
└─────────────────────────────────────────────────────────┘
```

## 2. [V3.1 & V3.4] LangGraph 迁移

### 概述

将 AI 编排层从手动工具调用模式迁移到 LangGraph 的 StateGraph 框架。

### 背景 (2025-12-05)

当前代码库已展示了可自然映射到 LangGraph 的类 Agent 模式。

### 架构决策记录 (2025-12-12)

**决策**: 确认采用 LangGraph，而非构建自定义框架。

**选择 LangGraph 的原因**:

| 因素 | 自定义框架 | LangGraph |
|------|-----------|-----------|
| 调试支持 | 仅靠代码注释 | Google/Stack Overflow/社区 |
| 文档资源 | 无外部资源 | 官方文档 + 教程 + 示例 |
| 未来维护 | 依赖原作者 | 行业标准，新开发者可快速上手 |
| 学习曲线 | 低（但调试难） | 中等（但有外部资源） |

### 实施方法

- **V3.1**: 预备重构 + 学习 LangGraph 基础
- **V3.3**: 应用于智能文档系统
- **V3.4**: 完成所有工作流迁移

| 当前模式                                       | LangGraph 对应            |
| ---------------------------------------------- | ------------------------- |
| 手动工具执行循环                               | `ToolNode`（自动）        |
| 分步状态（路由 → 查询 → 计算 → 评分 → 解释）   | `StateGraph` 节点 + 边    |
| 条件逻辑（数据充分？置信度通过？）             | 条件边                    |
| 每次请求状态                                   | 带注解的 Graph `State`    |

### 迁移收益

1. **对话记忆** — 目前只有 landing-chat 有历史记录；LangGraph 使所有模块都能轻松实现
2. **代理循环** — 启用重试/优化模式（如"首次失败则尝试另一个指标"）
3. **流式响应** — 在图执行时向 UI 发送中间结果
4. **更好的错误恢复** — 定义显式错误边，而非到处 try-catch
5. **可观测性** — LangGraph 的调试/追踪工具可视化图执行
6. **更清洁的代码** — 用声明式图替换 500+ 行的路由文件

### 当前架构分析

**已识别的隐式工作流**：

- 财务分析（6 步）
- 合规指导（5 步）
- 首页对话（4 步）

### 预备重构阶段

| 阶段 | 任务               | 优先级 | 说明                                     |
| ---- | ------------------ | ------ | ---------------------------------------- |
| A    | 提取显式状态类型   | 关键   | 创建 `workflow-states.ts`，为 StateGraph 做准备 |
| B    | 提取步骤函数       | 高     | 将路由处理器拆分为独立的纯函数           |
| C    | 集中工具定义       | 中     | 为 ToolNode 准备工具注册表               |
| D    | 整合类型           | 中     | 将分散的类型移到统一位置                 |
| E    | 创建错误类型层次   | 低     | 为条件边错误处理做准备                   |

### 为什么 LangGraph 需要 VPS

| LangGraph 功能   | Vercel 限制      | VPS 解决方案         |
| ---------------- | ---------------- | -------------------- |
| 多步骤推理       | 60s 超时         | 无超时               |
| 流式中间步骤     | 无 WebSocket     | 完全 WebSocket 支持  |
| 重试/优化循环    | 无状态，超时     | 持久进程             |
| 后台预处理       | 无后台任务       | PM2 工作进程         |

### 依赖项

- 预备重构无外部依赖
- LangGraph 迁移需要：`@langchain/langgraph`、`@langchain/core`

## 3. [V3.2 & V3.8] 安全增强

### 概述

V2 阶段 6 审计期间识别的安全改进。这些建议用于超出 MVP 演示的生产部署。

### 背景 (2025-12-03)

在 V2 部署准备期间进行了全面的安全审计。以下改进被识别但推迟到 V3。

### 当前状态 (V2 MVP)

**已实现**：

- ✅ 所有 7 个表启用 RLS
- ✅ 管理员密码验证
- ✅ Service key 仅服务端使用
- ✅ Supabase 参数化查询
- ✅ 客户端速率限制

**已知限制**：

- ⚠️ 无服务端速率限制
- ⚠️ 明文密码比较
- ⚠️ API 响应中暴露详细错误信息
- ⚠️ 无输入长度验证
- ⚠️ 缺少安全头

### 安全增强路线图

#### [V3.2] 第一优先级：关键（生产必需 - 已完成）

| 增强               | 描述                   |
| ------------------ | ---------------------- |
| **服务端速率限制** | 防止 API 滥用和 DoS    |
| **输入长度验证**   | 防止过大请求           |
| **错误信息脱敏**   | 防止信息泄露           |
| **密码哈希**       | 使用 bcrypt 存储哈希密码       |
| **会话令牌**       | 替代每次请求的密码认证         |
| **暴力破解防护**   | 指数退避 + 账户锁定            |

#### [V3.8] 第二优先级：高（后续）

| 增强               | 描述                           |
| ------------------ | ------------------------------ |
| **文件路径验证**   | 防止路径遍历攻击               |
| **安全头**         | CORS, CSP, X-Frame-Options     |
| **文件内容验证**   | 魔数检查                       |
| **审计日志**       | 跟踪管理员操作                 |
| **函数搜索路径**   | 修复 Supabase 函数警告         |

### 与 VPS 迁移的集成

迁移到 VPS 后，安全增强变得更容易：

- Redis 可在 VPS 上本地运行
- 无 serverless 对会话管理的约束
- 更好的日志和监控选项
- 可在 nginx 层实现基于 IP 的封禁

## 4. [V3.3] 智能文档系统

### 概述

用 AI 驱动的自动文档发现和选择替代手动文档选择。

### 背景讨论 (2024-12-03)

两个关键洞察推动了此设计：

1. **多期间数据**：AI 应该理解并从同一文档中提取两个期间的数据。
2. **文本型财务数据**：AI 需要自动从财务报表附注中查找和提取关键数据。

### 当前架构 vs 目标架构

**V2（当前）**：

```
用户 → 手动选择文档 → AI 从选定文档中提取 → 计算
```

**V3（目标）- 方案 C：智能默认 + 手动覆盖**：

```
用户问题 → AI 理解数据需求 → AI 搜索文档 → AI 多源提取 → 计算并显示来源
                                                            ↓
                                               [用户可覆盖文档选择]
```

### 现有基础设施（V2 已构建）

| 组件         | 状态      | 备注                              |
| ------------ | --------- | --------------------------------- |
| 向量嵌入     | ✅ 已存在 | `document_chunks.embedding` 列    |
| 多期间存储   | ✅ 已存在 | `financial_data.metric_value_previous` 列 |
| 语义搜索     | ✅ 已存在 | 可按相似度查询 `document_chunks`  |
| 关键词       | ✅ 已存在 | `document_chunks.keywords` 列     |

### 需要的新组件

1. **新文档类型**：`annual_report`（年度报告）、`financial_notes`（财务附注）
2. **文档搜索 API**：向量相似度 + 关键词匹配
3. **多文档提取**：结构化表格 + 文本附注的合并提取
4. **来源透明化 UI**：显示 AI 选择的文档，允许用户覆盖

## 5. [V3.5] 财务 Agent 逻辑升级

### 概述

在 V3.4 阶段，项目已经引入 LangGraph 框架，这为实现 Agent 能力提供了良好基础。V3.5 旨在将现有的线性工作流升级为具备记忆和推理能力的 **Agent（智能体）工作流**。

### 问题分析

项目当前的各个功能模块只能按照即定编排运行和调用不同功能（START -> Route -> Query -> Calc -> END），而无法自主选择实施路径和调用功能。这导致了：

1. **无记忆**：无法进行多轮对话比较（如“与去年相比”）。
2. **单步执行**：无法一次性解决复杂的多步问题（如“计算流动比率和速动比率”）。

### 升级目标

1. **引入循环 (Cycles)**: 允许 Agent 在 ToolNode 和 AgentNode 之间循环，直到完成任务。
2. **上下文记忆 (Memory)**: 在 State 中存储 `messages`，支持多轮对话。
3. **多工具调用**: 支持单次请求中并行或顺序调用多个工具。

## 6. [V3.6] 现代 Agent 交互重构

### 概述

重构现有 UI/UX，打造统一的 Agent 工作台，支持流式响应和多模态交互，以匹配 V3.5 强大的后端能力。

### 核心变更

#### 统一工作台 (Unified Workspace)

- **Super Agent 模式**：单一对话入口，根据用户意图自动调度"财务分析"、"合规指导"等子能力。
- **完全替换分模块导航**：移除 `/data-extract`、`/financial-analysis`、`/guidance-chat`，统一为 `/chat`。
- **混合意图处理**：支持在一个会话中同时处理查询、分析和合规问题。
- **信息提取作为工具**：用户在对话中上传文件，Agent 自动调用提取工具。

#### 流式响应与 WebSocket

- **实时思考过程**：通过 WebSocket 实时推送 Agent 的 Graph 执行状态（Thinking -> Action -> Observation）。
- **降低焦虑**：对于长耗时任务（如跨年财报对比），让用户看到系统在工作，而不是静止加载。

### 核心架构洞察 (2025-12-23)

**关键发现**: 现有三个"模块"在 LangGraph 层面并非本质不同：

- 相同的 Graph 结构 (agent → tool → agent 循环)
- 相同的工具执行机制 (toolRegistry)
- 仅系统提示词和工具子集不同

**结论**: 采用**扁平工具架构**，无需子 Agent。"模块"概念消解为"工具类别"。

### 分阶段实施 (2025-12-23 确认)

| 阶段 | 目标 | 交付物 |
|------|------|--------|
| **V3.6a** | 统一 Agent + 扁平工具 | 后端 API 可用，无流式 |
| **V3.6b** | WebSocket 流式响应 | 实时思考过程可见 |
| **V3.6c** | 统一对话 UI | 完整前端体验 |

### 页面路由变更

| 路由 | 当前 | V3.6 后 |
|------|------|---------|
| `/` | 营销 Landing | 保留 + "开始对话" CTA |
| `/chat` | 不存在 | **新增**: 统一对话工作台 |
| `/data-extract` | 信息提取 | **移除** |
| `/financial-analysis` | 财务分析 | **移除** |
| `/guidance-chat` | 合规指导 | **移除** |
| `/documents` | 文档管理 | 保留 |

### 实现依赖

- **VPS**：利用 V3.0 已建立的 VPS 环境支持 WebSocket 长连接。
- **LangGraph**：利用 `stream_mode="updates"` 获取中间状态。
- **V3.5 Agent**：工具调用和记忆能力。

### 详细文档

- PRD: `docs/V3.6_PHASE1_PRD.md`

## 7. [V3.7] 管理用财报体系

### 概述

实现**管理用财报体系**（Management Financial Statement System），将传统财务报表重构以进行更深入的分析。

### 背景讨论 (2024-12-03)

分析了当前财务数据是否足以构建管理体系指标。

#### 数据可用性分析

| 类别               | 指标                                                  | 数据状态                          |
| ------------------ | ----------------------------------------------------- | --------------------------------- |
| **资产负债表重构** | 净经营资产, 净负债                                    | ⚠️ 需要经营/金融分类逻辑         |
| **利润表重构**     | 税前经营利润, 税后经营净利润, 税后利息费用            | ✅ 可用（可计算税率）            |
| **现金流量表重构** | 营业现金毛流量, 营业现金净流量, 实体现金流量          | ❌ 需要折旧与摊销、期间对比       |
| **管理用比率**     | 净经营资产净利率, 税后利息率, 净财务杠杆, 管理用ROE   | ⚠️ 依赖上述数据                  |

### 已识别的关键挑战

1. **经营与金融分类**：需要业务逻辑来分类资产/负债
2. **折旧与摊销**：需从财务报表附注中查找，依赖智能文档系统
3. **期间对比数据**：数据库已支持 `metric_value_previous` 列
4. **税率计算**：可计算，需处理利润为负的边界情况

### 实现依赖

此功能依赖于[智能文档系统](#4-v33-智能文档系统)和[财务 Agent 逻辑升级](#5-v35-财务-agent-逻辑升级)，因为：

- 折旧与摊销数据在文本型年度报告中，需要 AI 自动提取。
- 复杂指标计算（如 ROI）往往涉及跨报表数据，Agent 的多步推理能力是必需的。

### 建议的实现阶段

1. **阶段 1**：实现资产/负债分类逻辑
2. **阶段 2**：添加利润表重构（当前数据可行）
3. **阶段 3**：集成智能文档系统以实现现金流量表重构
4. **阶段 4**：完成管理用比率和管理用ROE

### 计划属性

| 属性 | 详情 |
