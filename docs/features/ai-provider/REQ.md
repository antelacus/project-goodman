# REQ — ai-provider

## 1 概述

### 1.1 需求背景 [冻结]

goodman 的 AI 调用全部走 OpenAI 官方 API，该账号额度已用尽，对话、报告分析、信息提取、上传与文档检索都已不可用。项目改用第三方 relay（OpenAI 兼容接口、按 token 计费、不提供 embedding）。

不可用期间暴露了两个问题：报告章节的 AI 分析失败时，兜底文字写成"各项指标表现正常"，与实际数据无关，用户看到的是编造的结论；法规检索只返回文档切块，出处一律是 `"Unknown Source"`，用户无法知道答案出自哪部准则的哪一条。

本 feature 让 AI 恢复可用，并且让用户看到的每一句分析要么来自真实的模型输出、要么明确标为失败，每一条法规答案要么给出可核对的出处、要么明确标为不是来自资料库。使用者是会计部门的财务人员，他们拿回答去做账务处理与合规判断。

### 1.2 范围

- 做：
  - 所有 AI 调用改走 relay，统一使用 `gpt-6.1-sol`
  - AI 调用失败时如实显示失败
  - 去掉 embedding，法规检索改为对结构化条款的中文关键词检索，agent 可多轮检索
  - 修正条款拆分规则，45 部法规与准则重新拆分
  - 回答给出法规出处，并能打开原文
  - 资料库外的问题按规则作答
  - 上传与文档检索恢复可用
  - 删除不再使用的向量数据与相关数据库函数
- 明确不做：
  - 发布流水线（顺延，见 `docs/features/release-pipeline/TRACK.md`）
  - 报告与对话的耗时优化（本版只测量，§6.2）
  - 失败章节的单独重试、报告重新生成等新功能
  - staging 与生产的数据库隔离（属于发布流水线）

### 1.3 参考

- 报告章节与指标：`docs/versions/v4/v4_DEVELOPMENT_PLAN.md`
- 技术债：`docs/TECHNICAL_DEBT.md` TD-030（编造结论）、TD-024（报告耗时）、TD-021（LLM 用量）

## 3 用例

- 财务人员在工作台问法规问题（如"客户欠款收不回来怎么记账"），得到带《准则名》第 X 条出处的回答，并能点开原文核对。
- 财务人员问资料库里没有的法规，得到标注为"不是来自资料库"的参考回答，不含条款号。
- 财务人员问公司资料（财报、制度），得到基于资料库文档的回答；也可以选中自己上传的文档，就它提问。
- 财务人员生成财务分析报告：每个章节有指标表和 AI 分析；AI 失败时看到失败提示，而不是编造的分析。
- 财务人员上传财务报表，系统提取数据并写入财务数据；提取失败时看到失败，不写入数据。

## 5 功能需求

### 5.1 改走 relay（F1）

- 规则：
  - 对话、报告章节分析与摘要、信息提取、会话标题、报告配置解析，全部使用 `gpt-6.1-sol`。模型名住配置，这里只定口径：本版不为任何用途选用其他模型。
  - 调用参数按 OpenAI 官方新模型的要求：输出上限在 Chat Completions 用 `max_completion_tokens`、在 Responses API 用 `max_output_tokens`；不传 `temperature`。relay 当前接受旧参数，但不以此为准。
  - 每次 AI 调用都带系统提示词：Chat Completions 用系统消息，Responses API 用 `instructions`。不带时 relay 会注入约 4200 token 的 Codex 编程 agent 提示词，模型会以编程助手的身份作答。
- 验收判据：
  - §relay-model 每个 AI 用途解析出的模型都是 `gpt-6.1-sol`
  - §relay-params Chat Completions 调用带 `max_completion_tokens`，Responses API 调用带 `max_output_tokens`；所有调用都不含 `max_tokens` 与 `temperature`
  - §system-prompt 所有 Chat Completions 调用的第一条消息都是非空的系统消息；所有 Responses API 调用都带非空的 `instructions`

### 5.2 AI 失败不编造（F2）

"AI 失败"指以下任一情形：
- 报错，且重试用尽（最多重试 1 次）
- 超过该用途的时限（时限取值住配置）
- 输出未正常结束：因长度上限被截断、被拒绝、被内容过滤
- 应有文字而文字为空；应有 JSON 而无法解析或不符合 schema；工具调用的参数无法解析

只含工具调用、没有正文的回复是正常的，不是失败。截断的半截输出一律按失败处理，不得进入报告、提取或回答。

- 规则：
  - 报告的指标表由程序计算，不依赖 AI。某一章节的 AI 分析失败时，该章照常显示指标表，分析部分显示失败提示。
  - 只要有一个章节失败，摘要就不生成结论，显示"摘要未生成"。
  - 摘要自身的 AI 调用失败时，同样显示"摘要未生成"，不用兜底文字冒充结论。
  - 对话中 AI 失败时，显示明确的失败提示，不显示 SDK 的原始报错。回答是整段返回的（不逐字流式），所以 agent 任何一轮失败，用户都收不到回答，只收到失败提示；过程日志中已完成的步骤照常保留。
  - 信息提取失败时，上传结果报告失败，不向财务数据写入任何行。一份报表含多个期间时，所有期间都通过校验后才一次写入；任一期间失败，已通过的期间也不写入。
  - relay 挂起时，用户在该用途的时限内收到失败提示，而不是一直等待。
  - 会话标题生成失败时，用首条消息截断作标题（这不是分析，不算编造）。
- 硬错误（响亮失败）：
  - 章节分析失败 → `分析生成失败（AI 服务不可用）`
  - 摘要不生成 → `摘要未生成：部分章节的分析生成失败` / `摘要未生成：AI 服务不可用`
  - 对话失败 → `AI 服务暂时不可用，请稍后再试`
  - 信息提取失败 → `数据提取失败（AI 服务不可用），未写入任何数据`
- 验收判据：
  - §report-section-failure 一个章节的 AI 调用失败：该章含指标表与 `分析生成失败（AI 服务不可用）`；报告任何位置都不出现"各项指标表现正常"之类的兜底分析
  - §report-summary-failure 任一章节失败，或摘要调用失败：摘要显示"摘要未生成"，关键发现为空
  - §chat-failure 对话的 AI 调用失败：用户收到 `AI 服务暂时不可用，请稍后再试`
  - §extract-failure 信息提取的 AI 调用失败，或多期间中第二期校验失败：用户上传与管理员上传都报告失败，财务数据行数不变
  - §ai-outcome 输出因长度上限截断、被拒绝、文字为空、JSON 不符合 schema 时都按失败处理；只含工具调用的回复不算失败
  - §ai-timeout relay 不响应时，调用在时限内失败，用户收到失败提示
  - §smoke-report staging 冒烟生成的报告中只要有一个章节失败，冒烟即不通过

### 5.3 法规关键词检索（F3）

- 规则：
  - 法规检索的对象是结构化条款（45 份法规与准则，按 §5.6 重新拆分），不再是文档切块。
  - 中文关键词检索要能分词：查询"金融资产减值"要能命中写有"金融资产"与"减值"、但两词不相邻的条款。
  - agent 每次检索给出 1–8 个关键词，每个 2–10 个字；口语由 agent 改写成准则术语。
  - agent 第一次检索不理想时，可以换一种说法再检索，每个问题最多 3 次。次数用完后，agent 不能再检索，必须基于已有结果作答；"次数已用完"与"未找到"是两种不同的结果。
  - 检索结果中的每一条都带法规名、条款号与原文档标识。
- 验收判据：
  - §reg-search-citation 每条法规检索结果都含非空的法规名、条款号与原文档标识
  - §search-rounds 单个问题中执行的检索不超过 3 次：第 4 次请求得到"检索次数已用完"（不同于"未找到"），之后的作答轮次不再提供检索工具；保存的对话历史中没有未配对的工具调用
  - §keyword-match 在数据库中，关键词"金融资产""减值"能命中两词不相邻的条款
  - §retrieval-quality 测试查询集（约 20 条：10 条法规类，原文术语与口语化问法各半；6 条公司资料类；4 条资料库外）上，连续两轮评测都满足（模型每次选的关键词不同，一轮的结果波动大）：
    - 资料库内的 16 条中，≥ 90% 的查询在任一轮检索的前 5 条结果中包含预期的条款或文档
    - 资料库外的 4 条全部按 §5.5 作答
    - 查询集由 Claude 起草、Jason 审定；"预期的条款或文档"以 Jason 审定的为准

### 5.4 出处（F4）

- 规则：
  - 每条检索结果带一个编号（如 `[R3]`）。模型引用法规时只写编号，不自己写条款号；程序把编号替换成《法规名》第 X 条，并附原文链接。
  - 回答中不是由编号生成的条款号（"第 X 条"）一律视为未经核实：程序删去它所在的句子，并在回答末尾提示。
  - 不存在的编号同样视为未经核实。
  - 过程日志中的检索事件给出原文档链接，点开即为原文档预览。
- 硬错误：删去未核实的引用 → 回答末尾提示 `（已删去 N 处未经资料库核实的条款引用）`
- 验收判据：
  - §citation-text 回答中出现的每一个条款号都来自本问题的检索结果；模型自写的条款号或不存在的编号被删去并提示
  - §citation-link 法规检索事件在过程日志中带有原文档的预览链接，打开得到的是该条款所在的原文件

### 5.5 资料库外作答（F5）

- 规则：资料库中没有答案时（检索为空，或检索到的内容不能回答问题），agent 可以凭模型自己的知识作答，但必须：
  - 在回答开头标注 `以下内容不是来自资料库，未经条款核对`
  - 不写出任何条款号（如"第 X 条"），因为它们无法核对，最容易被编造
- 是否属于资料库外，由程序按引用判定：最终回答中没有任何有效编号时，程序在开头加上标注（模型已写则不重复）；条款号按 §5.4 删去。
- 检索出错不能当作"资料库里没有"：本问题的检索全部出错时，开头标注改为 `法规检索暂时失败，以下内容未经资料库核对`。
- 验收判据：
  - §out-of-library 没有有效编号的回答，开头含资料库外标注，正文不出现条款号格式；评测中 4 条资料库外问题都如此
  - §retrieval-error 本问题的检索全部出错时，回答开头是检索失败的标注，而不是资料库外的标注

### 5.6 条款重新拆分（F6）

现有的结构化条款不能直接用作出处：拆分规则把正文中的交叉引用（"按照本准则第二十五条的规定……"）也当成条款的开头，于是一条条款的后半段被贴上被引用条款的条款号。

- 规则：
  - 只有位于行首的"第X条"才是条款的开头；正文中的"第X条"是引用，不切分。
  - 同一部法规内，条款号按出现顺序逐一连续（第一条、第二条……），没有重复、没有跳号。章、节标题与页码行不属于任何条款的内容。
  - 去掉章节标题与页码行之后，第一条之后的每一行正文恰好属于一条条款，没有无归属的正文。
  - 抽取得到的页数必须等于 PDF 的页数，否则整份停下，不拆分。
  - 拆分对象是 Storage 中的原文件，不是文档切块。45 部全部重新拆分后替换表中的现有数据，替换前先备份。
  - 替换按文档进行，每份文档的删旧与插新在同一个数据库事务里；中途中断后可从头重跑，不会留下空文档或半套条款。替换前核对文档集合与原文件未变。
  - 从开始核对到 v4.7.0 上线，不在生产上传或删除法规（Jason）：生产上的旧版本仍用旧规则拆分。
  - 管理员上传法规时，用同一套拆分规则；原文件存入 Storage 失败时，上传失败，不写入文档与条款。
  - 核对程序给出的异常（例如原文本身跳号）列成清单交 Jason 判断，每一条都要有结论：修正规则、手工修正，或从检索中排除。
- 硬错误（响亮失败）：管理员上传的法规拆分后出现重复条款号 → 上传失败，提示 `条款拆分异常：第X条重复`，不写入任何条款
- 验收判据：
  - §reg-split-rule 正文中含"按照本准则第X条的规定"的条款，不会在引用处被切开
  - §reg-integrity 45 部重新拆分后，每部法规的条款号逐一连续、无重复；抽取页数等于 PDF 页数；没有无归属的正文；异常清单上的每一条都有 Jason 的结论
  - §reg-upload-dup 上传的法规拆出重复条款号时，上传失败且不写入条款
  - §reg-upload-storage 管理员上传法规时原文件存储失败：上传失败，不写入文档与条款

### 5.7 上传与文档检索（F7）

- 规则：
  - 上传时不再生成向量，切块照常写入。
  - 文档检索只检索资料库中状态为就绪的知识文档，并且不含法规和会计准则（文档类型为法律法规、会计准则）；改为中文关键词检索，分词要求同 §5.3。这一范围固定在数据库查询里，不受 agent 参数影响。
  - 法规和准则的原文只能经法规检索读到，读到的每一条都带证据编号（§5.4）。若文档检索也能读到同样的原文，模型会据此作答而没有可核对的出处，也不会触发资料库外标注。
  - 用户自己上传的文档不进检索：用户在对话中选中它，全文随问题一起交给模型（现有行为，不变）。把用户文档纳入检索需要按归属隔离，是新功能，不在本版。
- 验收判据：
  - §upload-no-embedding 用户上传一份文档：成功，切块写入，过程中没有 embedding 调用；在对话中选中它后，模型能读到其内容
  - §doc-search 资料库中的文档可以按其中的词语检索到；同一个词也出现在用户上传的文档或未就绪的文档里时，检索只返回资料库中就绪的文档
  - §doc-search-no-regulation 同一个词出现在法规或准则的文档切块里时，文档检索不返回它们，即使参数指定了这两种文档类型

### 5.8 去掉 embedding（F8）

- 规则：
  - 代码中不再有 embedding 调用，也不再有 embedding 模型配置。
  - 向量列与向量检索函数在生产验证 v4.7.0 检索正常之后删除（Phase 6）。删除不可逆，Jason 已同意。
- 验收判据：
  - §no-embedding-calls `src/` 中没有 embedding 接口的调用与配置
  - §vector-removed 删除后，数据库中不再有向量列与向量检索函数

## 6 其他需求

### 6.1 数据与安全

- staging 与生产共用一个数据库，迁移在 staging 执行时即作用于生产，而那时生产上运行的是 v4.6.4。因此本版的迁移只做添加，不删除、不修改 v4.6.4 在用的结构；删除只在 §5.8 规定的时点做。
- 本版不扩大 staging 对生产数据的写入。
- 例外：§5.6 替换结构化条款表的数据。v4.6.4 不读这张表（只在上传时写入、删除文档时清除），替换不影响运行中的生产；替换期间的上传冻结见 §5.6。
- 生产库的文档都是公开数据，经 relay 传输可接受。测试用合成数据；§retrieval-quality 的评测在真实的资料库上经 relay 运行，不进 CI，且不向数据库写入任何数据（不建会话、不存消息）。
- relay 的密钥与地址只在 `.env` 中，不进代码、不进对话。

### 6.2 性能

只测量、不设门槛。Phase 4 记录对话与报告生成耗时的 P50 / P95；报告耗时记入 TD-024，对话耗时没有基线，作为首次测量记录。

## 7 对外接口

- **relay**（输入/输出）：OpenAI 兼容的 Chat Completions 与 Responses API。能力与限制见 `DESIGN.md` §8。
