# REQ — ai-provider

## 1 概述

### 1.1 需求背景 [冻结]

goodman 的 AI 调用全部走 OpenAI 官方 API，该账号额度已用尽，对话、报告分析、信息提取、上传与文档检索都已不可用。项目改用第三方 relay（OpenAI 兼容接口、按 token 计费、不提供 embedding）。

不可用期间暴露了两个问题：报告章节的 AI 分析失败时，兜底文字写成"各项指标表现正常"，与实际数据无关，用户看到的是编造的结论；法规检索只返回文档切块，出处一律是 `"Unknown Source"`，用户无法知道答案出自哪部准则的哪一条。

本 feature 让 AI 恢复可用，并且让用户看到的每一句分析要么来自真实的模型输出、要么明确标为失败，每一条法规答案要么给出可核对的出处、要么明确标为不是来自资料库。使用者是会计部门的财务人员，他们拿回答去做账务处理与合规判断。

### 1.2 范围

- 做：
  - 所有 AI 调用改走 relay，统一使用 `gpt-6.1-sol`
  - AI 调用失败时如实显示失败
  - 去掉 embedding，法规检索改为对结构化条款的中文关键词检索，agent 可多轮检索
  - 回答给出法规出处，并能打开原文
  - 资料库外的问题按规则作答
  - 上传与文档检索恢复可用
  - 删除不再使用的向量数据与相关数据库函数、Edge Function
- 明确不做：
  - 发布流水线（顺延，见 `docs/features/release-pipeline/TRACK.md`）
  - 报告与对话的耗时优化（本版只测量，§6.2）
  - 失败章节的单独重试、报告重新生成等新功能
  - staging 与生产的数据库隔离（属于发布流水线）
  - 结构化条款的重新拆分（本版只核对，§5.6）

## 3 用例

- 财务人员在工作台问法规问题（如"客户欠款收不回来怎么记账"），得到带《准则名》第 X 条出处的回答，并能点开原文核对。
- 财务人员问资料库里没有的法规，得到标注为"不是来自资料库"的参考回答，不含条款号。
- 财务人员问公司资料（财报、制度），得到基于已上传文档的回答。
- 财务人员生成财务分析报告：每个章节有指标表和 AI 分析；AI 失败时看到失败提示，而不是编造的分析。
- 财务人员上传财务报表，系统提取数据并写入财务数据；提取失败时看到失败，不写入数据。

## 5 功能需求

### 5.1 改走 relay（F1）

- 规则：
  - 对话、报告章节分析与摘要、信息提取、会话标题、报告配置解析，全部使用 `gpt-6.1-sol`。模型名住配置，这里只定口径：本版不为任何用途选用其他模型。
  - 调用参数按 OpenAI 官方新模型的要求：输出上限用 `max_completion_tokens`，不传 `temperature`。relay 当前接受旧参数，但不以此为准。
  - 每次 AI 调用都带系统提示词：Chat Completions 用系统消息，Responses API 用 `instructions`。不带时 relay 会注入约 4200 token 的 Codex 编程 agent 提示词，模型会以编程助手的身份作答。
- 验收判据：
  - §relay-model 每个 AI 用途解析出的模型都是 `gpt-6.1-sol`
  - §relay-params 所有 AI 调用都不含 `max_tokens` 与 `temperature`
  - §system-prompt 所有 Chat Completions 调用的第一条消息都是非空的系统消息；所有 Responses API 调用都带非空的 `instructions`

### 5.2 AI 失败不编造（F2）

"AI 失败"指 SDK 重试用尽后仍报错、超时，或返回空内容。

- 规则：
  - 报告的指标表由程序计算，不依赖 AI。某一章节的 AI 分析失败时，该章照常显示指标表，分析部分显示失败提示。
  - 只要有一个章节失败，摘要就不生成结论，显示"摘要未生成"。
  - 摘要自身的 AI 调用失败时，同样显示"摘要未生成"，不用兜底文字冒充结论。
  - 对话中 AI 失败时，显示明确的失败提示。不显示半截内容冒充完整回答：流式输出中途失败时，已输出的部分之后追加失败提示。
  - 信息提取失败时，上传结果报告失败，不向财务数据写入任何行。
  - 会话标题生成失败时，用首条消息截断作标题（这不是分析，不算编造）。
- 硬错误（响亮失败）：
  - 章节分析失败 → `分析生成失败（AI 服务不可用）`
  - 摘要不生成 → `摘要未生成：部分章节的分析生成失败` / `摘要未生成：AI 服务不可用`
  - 对话失败 → `AI 服务暂时不可用，请稍后再试`
  - 信息提取失败 → `数据提取失败（AI 服务不可用），未写入任何数据`
- 验收判据：
  - §report-section-failure 一个章节的 AI 调用失败：该章含指标表与 `分析生成失败（AI 服务不可用）`；报告任何位置都不出现"各项指标表现正常"之类的兜底分析
  - §report-summary-failure 任一章节失败，或摘要调用失败：摘要显示"摘要未生成"，关键发现为空
  - §chat-failure 对话的 AI 调用失败：用户收到 `AI 服务暂时不可用，请稍后再试`
  - §extract-failure 信息提取的 AI 调用失败：上传报告失败，财务数据行数不变
  - §smoke-report staging 冒烟生成的报告中只要有一个章节失败，冒烟即不通过

### 5.3 法规关键词检索（F3）

- 规则：
  - 法规检索的对象是结构化条款（45 份法规与准则、1559 条），不再是文档切块。
  - 中文关键词检索要能分词：查询"金融资产减值"要能命中写有"金融资产"与"减值"、但两词不相邻的条款。
  - agent 第一次检索不理想时，可以换一种说法再检索，每个问题最多 3 轮。3 轮仍未找到，按 §5.5 作答。
  - 检索结果中的每一条都带法规名、条款号与原文档标识。
- 验收判据：
  - §reg-search-citation 每条法规检索结果都含非空的法规名、条款号与原文档标识
  - §search-rounds 单个问题中的检索调用不超过 3 次
  - §retrieval-quality 测试查询集（约 20 条：10 条法规类，原文术语与口语化问法各半；6 条公司资料类；4 条资料库外）上：
    - 资料库内的 16 条中，≥ 90% 的查询在任一轮检索的前 5 条结果中包含预期的条款或文档
    - 资料库外的 4 条全部按 §5.5 作答
    - 查询集由 Claude 起草、Jason 审定；"预期的条款或文档"以 Jason 审定的为准

### 5.4 出处（F4）

- 规则：
  - 回答引用法规时，正文写明《法规名》第 X 条。
  - 过程日志中的检索事件给出原文档链接，点开即为原文档预览。
  - 出处只能来自检索结果，不得由模型自拟。
- 验收判据：
  - §citation-text 基于检索结果作答的法规问题，回答正文包含检索结果中某条的法规名与条款号
  - §citation-link 法规检索事件在过程日志中带有指向该条款原文档的预览链接

### 5.5 资料库外作答（F5）

- 规则：资料库中没有答案时，agent 可以凭模型自己的知识作答，但必须：
  - 在回答开头标注 `以下内容不是来自资料库，未经条款核对`
  - 不写出任何条款号（如"第 X 条"），因为它们无法核对，最容易被编造
- 验收判据：§out-of-library 资料库外的问题，回答开头含该标注，正文不出现条款号格式

### 5.6 条款核对（F6）

- 规则：
  - 程序逐条核对：条款内容能在原文档中找到；同一部法规内条款号无重复、无跳号。
  - 异常清单交 Jason 判断。判为拆错的条款，在本版内修正或从检索中排除（由 Jason 裁定）。
- 验收判据：§reg-integrity 核对程序对 1559 条全部跑完，并输出异常清单；清单上的每一条都有 Jason 的结论

### 5.7 上传与文档检索（F7）

- 规则：
  - 上传时不再生成向量，切块照常写入。
  - 文档检索（公司资料与用户上传文档）改为中文关键词检索，分词要求同 §5.3。
- 验收判据：
  - §upload-no-embedding 上传一份文档：成功，切块写入，过程中没有 embedding 调用
  - §doc-search 上传后的文档可以按其中的词语检索到

### 5.8 去掉 embedding（F8）

- 规则：
  - 代码中不再有 embedding 调用，也不再有 embedding 模型配置。
  - 向量列、向量检索函数与 Edge Function `embed` 在生产验证 v4.7.0 检索正常之后删除（Phase 6）。删除不可逆，Jason 已同意。
- 验收判据：
  - §no-embedding-calls `src/` 中没有 embedding 接口的调用与配置
  - §vector-removed 删除后，数据库中不再有向量列与向量检索函数，Edge Function `embed` 不再存在

## 6 其他需求

### 6.1 数据与安全

- staging 与生产共用一个数据库，迁移在 staging 执行时即作用于生产，而那时生产上运行的是 v4.6.4。因此本版的迁移只做添加，不删除、不修改 v4.6.4 在用的结构；删除只在 §5.8 规定的时点做。
- 本版不扩大 staging 对生产数据的写入。
- 生产库的文档都是公开数据，经 relay 传输可接受。测试用合成数据；§retrieval-quality 的评测在真实的资料库上经 relay 运行，不进 CI。
- relay 的密钥与地址只在 `.env` 中，不进代码、不进对话。

### 6.2 性能

只测量、不设门槛。Phase 4 记录对话与报告生成耗时的 P50 / P95；报告耗时记入 TD-024，对话耗时没有基线，作为首次测量记录。

## 7 对外接口

- **relay**（输入/输出）：OpenAI 兼容的 Chat Completions 接口。能力与限制见 `TRACK.md` 外部约束。
  - 超时或报错：SDK 重试用尽后按 §5.2 失败。
  - 返回空内容：按失败处理。
  - JSON 无法解析：按失败处理，不用兜底内容填充。
- **structured_regulations**（输入）：由法规与准则原文拆分而来，表结构见 `src/lib/database/types.ts`。每条都关联到一份原文档，可以生成预览链接。
  - 内容与原文对不上，或条款号重复、跳号：按 §5.6 处理。
- **过程日志的来源链接**（输出）：读者是财务人员，用来打开原文、核对出处。
