# V3.5 需求声明：财务 Agent 逻辑升级

> **文档类型**: 需求声明 (Requirement Declaration)
> **版本**: V3.5
> **状态**: Phase 1 - 待审批
> **日期**: 2025-12-22
> **前置条件**: V3.4 (LangGraph 完整迁移) ✅ 已完成

---

## 1. 概述

### 1.1 背景

V3.4 已完成 LangGraph 框架迁移，建立了 StateGraph 工作流基础。当前各工作流仍为**线性执行**模式：

```
当前: START → 路由 → 查询 → 计算 → 响应 → END
```

这种模式存在两个核心限制：

1. **无记忆**: 无法进行多轮对话比较（如"与去年相比如何？"）
2. **单步执行**: 无法在单次请求中解决多步问题（如"计算流动比率和速动比率"）

### 1.2 目标

将现有线性工作流升级为具备**记忆**和**推理**能力的 Agent 工作流：

```
目标: START → Agent ⇄ Tools (循环直到完成) → 响应 → END
                ↑
          Memory (对话历史)
```

## 2. 功能需求

### 2.1 对话记忆 (Conversation Memory)

| 需求 | 描述 |
|------|------|
| **持久化存储** | 对话历史存储在 Supabase PostgreSQL 数据库 |
| **会话管理** | 每个对话有唯一 session_id，支持恢复历史上下文 |
| **上下文窗口** | 保留最近 N 条消息用于 LLM 上下文（可配置，默认 10 条） |
| **跨期间引用** | 支持"与去年相比"等时间相关的对话引用 |

**Session ID 生命周期**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  首次请求 (无 session_id)                                            │
│  ─────────────────────────                                          │
│  Frontend: POST /api/xxx { question: "..." }                        │
│  Backend:  生成新 session_id (UUID)                                  │
│            创建 conversation_sessions 记录                           │
│            处理请求                                                  │
│  Response: { ..., sessionId: "abc-123" }  ← 返回给前端               │
│                                                                     │
│  后续请求 (携带 session_id)                                          │
│  ─────────────────────────                                          │
│  Frontend: POST /api/xxx { question: "...", sessionId: "abc-123" }  │
│  Backend:  加载历史消息                                              │
│            处理请求（带上下文）                                       │
│  Response: { ..., sessionId: "abc-123" }                            │
└─────────────────────────────────────────────────────────────────────┘

关键设计决策：
- session_id 由后端生成（确保唯一性）
- 首次响应返回 session_id，前端需存储并在后续请求中传回
- session_id 可选：不传则创建新会话（向后兼容）
```

**使用场景示例**：

```
用户: 今年的流动比率是多少？
Agent: 2024年的流动比率是 1.85...

用户: 与去年相比如何？
Agent: [从记忆中获取上一轮的年份和指标]
       2023年的流动比率是 1.72，2024年增长了 7.6%...
```

### 2.2 Agent 循环 (Agent Loop)

| 需求 | 描述 |
|------|------|
| **循环执行** | Agent 与 Tools 之间循环，直到任务完成或达到上限 |
| **最大迭代** | 可配置的最大循环次数（**默认 5 次**） |
| **自主决策** | Agent 自主决定调用哪些工具、何时停止 |
| **状态追踪** | 每次循环记录工具调用和结果 |

**当前 vs 目标架构**：

```
当前 (Guidance Chat 内部实现):
┌─────────────────────────────┐
│  generateGuidance 节点       │
│  ┌─────────────────────────┐│
│  │  while (tool_calls) {   ││  ← 循环在节点内部
│  │    执行工具              ││
│  │  }                      ││
│  └─────────────────────────┘│
└─────────────────────────────┘

目标 (图级别循环):
┌──────────────┐    ┌──────────────┐
│  Agent Node  │ ⇄  │  Tool Node   │  ← 循环在图级别
└──────────────┘    └──────────────┘
```

**迭代次数设计考量**：

- 典型场景需要 2-3 次循环（思考 → 工具 → 响应）
- 复杂场景可能需要 4-5 次（多工具顺序调用）
- 默认 5 次在功能和成本之间取得平衡
- 每次 LLM 调用约 3-5 秒，5 次上限 ≈ 最大 25 秒延迟

### 2.3 多工具调用 (Multi-Tool Calling)

| 需求 | 优先级 | 描述 |
|------|--------|------|
| **顺序调用** | **P0 必须** | Tool A → 获取结果 → Tool B → 获取结果（稳定可靠） |
| **并行调用** | P1 可选 | Promise.all 同时执行多个独立工具（性能优化） |
| **结果聚合** | **P0 必须** | 多个工具结果整合为统一响应 |

**实现策略**：

1. **Phase 1**: 实现顺序调用，确保稳定性
2. **Phase 2 (可选)**: 如 LLM 返回多个 tool_calls，可考虑并行执行

**顺序调用场景示例**：

```
用户: 计算流动比率和速动比率

Agent 循环 1:
  思考: 需要计算流动比率
  调用: calculate_current_ratio(year=2024)
  结果: 1.85

Agent 循环 2:
  思考: 还需要计算速动比率
  调用: calculate_quick_ratio(year=2024)
  结果: 1.42

Agent 循环 3:
  思考: 两个指标都已计算完成
  响应: 流动比率 1.85，速动比率 1.42
```

## 3. 技术需求

### 3.1 适用范围

**全部 3 个工作流都需要升级**：

| 工作流 | 当前状态 | 升级需求 |
|--------|----------|----------|
| **Landing Chat** | 线性 4 节点 | + 记忆 |
| **Guidance Chat** | 条件 5 节点 + 节点内工具循环 | + 记忆 + 图级别循环 |
| **Financial Analysis** | 条件 5 节点 | + 记忆 + 图级别循环 + 多工具 |

### 3.2 数据库 Schema

**前置条件检查**：

```sql
-- 验证 pgcrypto 扩展（用于 gen_random_uuid）
-- 如果不存在，需要先启用
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

**新增对话历史表**：

```sql
-- 对话会话表
CREATE TABLE conversation_sessions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  workflow_type TEXT NOT NULL,  -- 'landing-chat', 'guidance-chat', 'financial-analysis'
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now(),
  metadata JSONB DEFAULT '{}'   -- 可存储工作流特定的上下文
);

-- 对话消息表
CREATE TABLE conversation_messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  session_id UUID REFERENCES conversation_sessions(id) ON DELETE CASCADE,
  role TEXT NOT NULL,           -- 'user', 'assistant', 'tool'
  content TEXT NOT NULL,
  tool_calls JSONB,             -- 工具调用记录
  tool_results JSONB,           -- 工具执行结果
  created_at TIMESTAMPTZ DEFAULT now(),
  sequence_number INTEGER NOT NULL
);

-- 索引
CREATE INDEX idx_messages_session ON conversation_messages(session_id, sequence_number);
CREATE INDEX idx_sessions_workflow ON conversation_sessions(workflow_type, created_at DESC);
```

### 3.3 Agent System Prompt 设计

**关键认识**: Agent 的"推理"和"自主决策"能力完全依赖于 System Prompt 的质量。

**Prompt 设计原则**：

| 要素 | 说明 |
|------|------|
| **角色定义** | 明确 Agent 是财务分析助手，具备哪些能力 |
| **工具说明** | 清晰描述每个工具的用途、参数、返回值 |
| **决策指南** | 什么情况下调用工具，什么情况下直接回答 |
| **终止条件** | 明确何时停止循环（任务完成、信息充足） |
| **上下文使用** | 如何利用对话历史理解用户意图 |

**Prompt 模板结构** (待 Phase 2 详细设计):

```
你是一个财务分析 Agent，具备以下能力：
1. 查询财务数据
2. 计算财务指标
3. 提供财务建议

## 可用工具
[工具列表及说明]

## 决策规则
- 如果用户询问具体指标，先查询数据再计算
- 如果用户引用"去年"、"上期"，从对话历史中获取上下文
- 如果已获得足够信息，直接生成回答，不再调用工具

## 终止条件
当以下任一条件满足时，生成最终回答：
- 用户问题已完整解答
- 所有必要计算已完成
- 达到工具调用上限
```

### 3.5 State 结构升级

```typescript
interface AgentState {
  // 输入
  input: {
    question: string;
    sessionId?: string;  // 可选: 会话ID（不传则创建新会话）
    // ... 其他现有字段
  };

  // Agent 循环状态 (新增)

    messages: Message[];           // 当前会话的对话历史

  };

  // 输出
  output: {
    response: string;
    sessionId: string;          // 新增: 返回会话ID给前端
    toolResults: ToolResult[];  // 工具执行结果
    // ... 其他现有字段
  };

  meta: WorkflowMeta;
}
```

## 4. 非功能需求

### 4.1 性能

| 指标 | 要求 |
|------|------|
| **循环延迟** | 每次 Agent-Tool 循环 < 5 秒 |
| **记忆加载** | 会话历史加载 < 200ms |
| **总响应时间** | 5 次循环上限 ≈ 最大 30 秒 |

### 4.2 可靠性

| 指标 | 要求 |
|------|------|
| **循环上限** | **默认 5 次**，可配置 |
| **超时保护** | 单次请求总超时 2 分钟 |
| **错误恢复** | 工具失败记录错误，继续下一循环 |

### 4.3 可观测性

| 需求 | 描述 |
|------|------|
| **循环日志** | 记录每次循环的工具调用和结果 |
| **性能追踪** | 各阶段耗时统计 |
| **调试信息** | Agent 决策过程可追溯 |

## 5. 测试策略

### 5.1 记忆功能验证 (无 UI 情况下)

由于 V3.5 不包含对话历史 UI，需要通过以下方式验证记忆功能：

**方法 1: API 级别测试脚本**

```typescript
// tests/memory-test.ts
async function testMemory() {
  // 第一次请求：不传 sessionId
  const res1 = await fetch('/api/financial-analysis', {
    method: 'POST',
    body: JSON.stringify({ question: '今年的流动比率是多少？' })
  });
  const data1 = await res1.json();
  const sessionId = data1.sessionId;  // 保存返回的 sessionId
  console.log('Session created:', sessionId);

  // 第二次请求：传入 sessionId
  const res2 = await fetch('/api/financial-analysis', {
    method: 'POST',
    body: JSON.stringify({
      question: '与去年相比如何？',
      sessionId: sessionId  // 传回 sessionId
    })
  });
  const data2 = await res2.json();

  // 验证：响应应包含去年对比（从记忆中获取上下文）
  assert(data2.response.includes('去年') || data2.response.includes('2023'));
}
```

**方法 2: 日志验证**

```
[Agent] Session abc-123: Loading 2 historical messages
[Agent] Context: Previous query was about "流动比率" for year 2024
[Agent] Interpreting "去年" as year 2023 based on context
```

**方法 3: 数据库直接查询**

```sql
-- 验证会话创建
SELECT * FROM conversation_sessions WHERE id = 'abc-123';

-- 验证消息存储
SELECT role, content, sequence_number
FROM conversation_messages
WHERE session_id = 'abc-123'
ORDER BY sequence_number;
```

### 5.2 Agent 循环验证

| 测试场景 | 预期行为 |
|----------|----------|
| 简单问题 | 1-2 次循环后完成 |
| 多指标问题 | 3-4 次循环（每个指标一次工具调用） |
| 达到上限 | 第 5 次循环后强制终止并返回已有结果 |
| 工具失败 | 记录错误，尝试替代方案或返回部分结果 |

## 6. 约束与依赖

### 6.1 技术约束

- **LangGraph 版本**: `@langchain/langgraph@^1.0.7`（当前已安装）
- **OpenAI Model**: `gpt-5-mini`（支持 function calling）
- **数据库**: Supabase PostgreSQL（已有）
- **pgcrypto**: 需验证扩展已启用

### 6.2 依赖项

| 依赖 | 状态 | 说明 |
|------|------|------|
| V3.4 LangGraph 迁移 | ✅ 完成 | StateGraph 基础架构已就绪 |
| 工具注册表 | ✅ 存在 | 需要与 Agent 集成 |
| 会话表 | ❌ 待创建 | 新数据库 schema |
| pgcrypto 扩展 | ⚠️ 待验证 | 用于 UUID 生成 |

### 6.3 风险识别

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| Agent 无限循环 | 资源耗尽 | 严格的 5 次循环上限 + 超时保护 |
| 对话历史过长 | Token 超限 | 滑动窗口（最近 10 条） |
| 工具调用失败 | 用户体验差 | 记录错误，继续执行 |
| Prompt 质量不足 | Agent 行为不当 | 迭代优化 Prompt，增加示例 |
| 延迟过高 | 用户等待 | 5 次上限控制在 30 秒内 |
