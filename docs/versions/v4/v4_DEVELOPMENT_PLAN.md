## 2. v4 战略方向

### 2.1 核心目标

**构建可信赖的 AI 财务助手**：财务工作要求高精度和准确性。用户必须能够验证 Agent 执行的每一步操作。

**核心原则**: 透明优先，功能其次。

### 2.2 策略：Transparency-First（透明优先）

| 策略 | 说明 |
|------|------|
| **透明为基** | 先实现过程透明化，建立用户信任基础 |
| **可验证性** | 每一步操作都可展开查看，支持人工核验 |
| **数据溯源** | 所有数据显示来源链接，可追溯至原始文件 |
| **渐进增强** | 在透明基础上，逐步添加报告生成、管理会计等功能 |

### 2.3 版本路线图

| 版本 | 主题 | 描述 | 状态 |
|------|------|------|------|
| **v4.0** | Agent 过程透明化 | 展示推理过程，可折叠/展开，数据源链接（信任基础） | ✅ 已发布 (2026-01-08) |
| **v4.1** | 工具体系精简 | 整合冗余工具，明确工具边界，提升 Agent 工具选择准确性 | ✅ 已发布 (2026-01-08) |
| **v4.2** | 报告生成系统 | 使用现有 21 个指标生成综合财务分析报告（核心展示功能） | ✅ 已发布 (2026-01-12) |
| **v4.3** | 项目基础增强 | 代码质量、文档更新、UI/UX、健壮性、测试、安全、日志 | ✅ 已发布 (2026-01-17) |
| **v4.4** | 生产就绪 | staging、集成测试、监控告警、架构/安全文档化 | ✅ 已发布 (2026-01-19) |
| **v4.5** | 生产就绪缺口补齐 | 指标/性能阈值、A11y/Lighthouse、文档一致性、安全审计门禁 | ✅ 已发布 (2026-01-20) |
| **v4.6** | 性能优化 | 功能正确性、稳定性与性能提升（含检索可靠性） | 待规划 |

## 3. 功能规划

### 3.1 [v4.0] Agent 过程透明化（日志输出增强）

| 属性 | 详情 |
|------|------|
| **目录** | `features/process-transparency/` |
| **描述** | 展示 Agent 工作过程，支持用户手动验证每一步操作 |
| **依赖** | v3 完成（已满足） |
| **状态** | ✅ 已发布 (2026-01-08) |

**设计理念**:

会计工作要求高精度。当 Agent 仅显示最终结果而不展示工作过程时，输出看起来可疑且不可靠。用户必须能够手动验证每一步。

**核心能力**:

1. **过程可视化**
   - 始终展示 Agent 工作过程：思考、工具调用、计算
   - 过程默认**折叠显示**（不干扰主要内容）
   - 每个步骤**可点击展开**，支持手动验证

2. **数据溯源**
   - 当 Agent 从数据库提取数据时，显示**原始内容链接**
   - 链接指向原始文件/文档来源
   - 为所有使用的数据建立审计追踪

3. **过程类别**
   - 🤔 思考/推理步骤
   - 🔧 工具调用（含参数）
   - 📊 计算步骤（公式 + 数值）
   - 📄 数据来源引用（含链接）

**UI 示意**:

```
┌─────────────────────────────────────────┐
│ 📊 流动比率计算结果: 2.15               │
│                                         │
│ ▶ 查看计算过程 (点击展开)               │
│   ┌─────────────────────────────────┐   │
│   │ 🤔 识别用户意图: 计算流动比率     │   │
│   │ 🔧 调用工具: current_ratio       │   │
│   │ 📄 数据来源: 2024年资产负债表    │ ← 可点击 │
│   │    流动资产: ¥1,234,567         │   │
│   │    流动负债: ¥573,891           │   │
│   │ 📊 计算: 1,234,567 ÷ 573,891    │   │
│   │ ✅ 结果: 2.15                    │   │
│   └─────────────────────────────────┘   │
└─────────────────────────────────────────┘
```

**技术方案**:

1. **后端：结构化事件日志**
   - 修改 LangGraph 工作流以发出结构化事件
   - 事件类型：`thinking`, `tool_call`, `tool_result`, `data_fetch`, `calculation`
   - 每个事件包含：时间戳、类型、内容、source_reference（如适用）

2. **前端：可折叠过程展示**
   - 新组件：`ProcessLog`（支持展开/折叠）
   - 按时间顺序渲染事件
   - 按事件类型设置样式（图标、颜色）
   - 可点击的来源链接

3. **数据源链接**
   - 查询 `financial_data` 时包含文档引用
   - 生成指向文档查看器或原始文件的链接

### 3.2 [v4.1] 工具体系精简

| 属性 | 详情 |
|------|------|
| **目录** | `features/tool-rationalization/` |
| **描述** | 整合冗余工具，明确工具边界，提升 Agent 工具选择准确性 |
| **依赖** | v4.0 过程透明化 |
| **状态** | ✅ 已发布 (2026-01-08) |

**背景**:

当前系统有 29 个工具，其中部分工具功能重叠，边界不清晰，导致 Agent 选择工具时可能出现混淆。

**问题分析**:

| 工具 | 数据源 | 问题 |
|------|--------|------|
| `get_financial_metric` | financial_data 表 | 与 query_financial_data 重叠 |
| `query_financial_data` | financial_data 表 | 与 get_financial_metric 重叠 |
| `calculate_financial_metric` | 用户提供数据 | 预设工具已含自动查询+计算 |

**解决方案**:

1. **合并**: `get_financial_metric` → 增强 `query_financial_data`（支持多年份）
2. **移除**: `calculate_financial_metric`（预设工具已覆盖此场景）
3. **保留**: 22 个预设工具、search_documents、extract_document、evaluate_expression
4. **增强**: 增强system prompt，明确工具边界

**精简后工具体系**:

```
结构化数据 (financial_data 表):
├── 22 个预设工具 (流动比率, ROE 等)
└── query_financial_data (增强版: 支持多指标 + 多年份)

非结构化数据 (documents 表):
├── search_documents (向量/关键词搜索)
└── extract_document (提取特定信息)

计算工具:
└── evaluate_expression (算术运算)

总计: 26 个工具 (原 29 个)
```

**Agent 决策树**:

```
用户问题
│
├─ 标准比率? (流动比率, 资产负债率等)
│   └─► 预设工具 (自动查询 financial_data)
│
├─ 原始指标数值? (货币资金, 净利润等)
│   └─► query_financial_data
│
├─ 文档中的信息? (货币资金明细, 管理层讨论)
│   └─► search_documents → extract_document
│
└─ 计算增长/变化/比较?
    └─► evaluate_expression
```

### 3.3 [v4.2] 报告生成系统

| 属性 | 详情 |
|------|------|
| **目录** | `features/report-generation/` |
| **描述** | AI Agent 自主编排多个财务分析工具，生成结构化专业报告（含完整过程可视化） |
| **依赖** | v4.1 工具体系精简 |
| **状态** | ✅ 已发布 (2026-01-12) |

**核心能力**:

- Agent 接收高级指令 → 自主决定分析内容 → 生成结构化报告
- 综合财务分析报告（流动性、偿债能力、盈利能力、效率）
- 经营建议报告（基于财务数据的业务建议）
- **所有分析过程透明可见**（基于 v4.0）

**报告格式**:

结构化章节：执行摘要 → 分析章节 → 关键发现 → 建议

**技术方案**:

创建元工具 `generate_report`：

1. 接收报告类型和参数
2. 内部调用多个计算工具（current_ratio, ROE 等）
3. 将结果综合为结构化 Markdown 输出
4. 所有步骤记录到过程日志
