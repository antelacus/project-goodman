# v4.5 性能优化 - Phase 1 需求文档

## 概述

| 属性 | 详情 |
|------|------|
| **功能名称** | 性能优化 (Performance Optimization) |
| **版本** | v4.5 |
| **依赖** | v4.4 生产就绪（staging + 观测能力） |
| **状态** | Phase 1 - 需求定义 |

---

## 问题陈述

当前项目在功能层面已覆盖核心场景，但仍存在“可用但不稳定”的问题：

1. **关键功能稳定性不足**：部分工作流偶发失败（Agent 检索、报告生成、提取流程）。
2. **性能不可控**：缺少端到端性能基线与明确的性能目标。
3. **回归风险**：缺乏系统化的回归验证，导致“修复一处、影响他处”的情况。
4. **功能说明与行为不一致**：部分工具/流程描述与实际行为存在偏差，影响可靠性。
5. **页面文案与视觉噪音**：存在装饰性过强或承诺不精准的展示，影响可信度。

v4.5 的目标是让“每个关键功能都能稳定工作”，并通过明确的成功率、错误率、性能指标进行量化验收。

---

## 范围

### 范围内

1. 定义“关键功能清单”与验收标准
2. 建立成功率/错误率/性能阈值（基于 staging 统计）
3. 关键路径稳定性优化（Agent 检索、报告生成、提取、Quick Actions、管理员流程）
4. 统一功能描述与行为（prompt/文案/工具说明）
5. 回归验证与自动化测试补齐
6. 页面文案与 UI 组件优化（逐页确定改动清单）

### 范围外

- 新增业务功能
- 大规模性能压测与容量规划
- 多区域部署与系统架构重构
- 数据备份/灾备体系

## 需求详情

### REQ-A1: 关键功能清单与验收标准

**目标状态**：
- 明确 v4.5 必须稳定的功能清单（P0/P1）
- 为每条功能定义“可验证”的验收标准

**验收标准**：
- [ ] 输出 P0 功能清单（至少：Agent 工作流、检索、提取、报告生成、Quick Actions、管理员核心流程）
- [ ] 输出 P1 功能清单（次要流程与辅助功能）
- [ ] 每个功能至少 1 条可执行的验收步骤

---

### REQ-A2: 成功率/错误率/性能基线

**基线阈值（方案 1）**：

- **成功率**：关键流程成功率 ≥ 98%
- **错误率**：5xx 错误率 ≤ 0.5%
- **性能（P95）**：
  - 非 AI 接口：< 1s
  - 聊天：首 token < 3s，整体 < 12s
  - 报告生成：< 60s
  - 文档提取：< 45s

**验收标准**：
- [ ] staging 统计口径明确（采样周期与样本量）
- [ ] 指标在 CI/日志中可被追踪
- [ ] 所有关键功能均可映射到上述指标

---

### REQ-B1: Agent 工作流稳定性

**目标状态**：
- Agent 在关键路径中具备稳定检索与数据回填能力
- 出错时可降级（清晰提示 + 可重试）

**验收标准**：
- [ ] Agent 检索成功率达到基线
- [ ] 检索失败时有可观测的错误与用户提示
- [ ] 关键路径（查询 → 计算 → 展示）不中断

---

### REQ-B2: 检索可靠性与数据一致性

**目标状态**：
- 统一检索入口行为（文档检索 + structured 查询）
- 结果可追溯、可验证

**验收标准**：
- [ ] 关键检索请求在日志中有明确指标
- [ ] 对已存在的示例数据检索结果稳定可复现
- [ ] 出现空结果时有清晰解释/引导

---

### REQ-C1: 文档提取稳定性

**目标状态**：
- 上传/提取流程稳定且可追踪
- 异常场景有明确错误提示

**验收标准**：
- [ ] P95 < 45s
- [ ] 失败时返回标准错误结构
- [ ] 关键路径可通过集成测试覆盖

---

### REQ-C2: 报告生成稳定性

**目标状态**：
- 报告生成流程稳定完成，避免中途失败

**验收标准**：
- [ ] P95 < 60s
- [ ] 报告生成失败率 ≤ 2%
- [ ] SSE/流程日志完整可用

---

### REQ-C3: Quick Actions 与管理员流程稳定性

**目标状态**：
- Quick Actions 功能输出稳定且符合描述
- 管理员操作流程稳定（上传/配置）

**验收标准**：
- [ ] Quick Actions 输出与描述一致
- [ ] 管理员关键流程具备集成测试

---

### REQ-D1: 功能描述一致性修复

- 工具描述、UI 文案、实际行为一致

**验收标准**：

- [ ] 不再出现“支持但实际不可用”的描述

---

### REQ-D2: 回归验证与测试覆盖

**目标状态**：
- 关键功能具备自动化回归覆盖

**验收标准**：

- [ ] 覆盖率报告可生成并追踪

### REQ-E1: 性能回归监控

### REQ-F1: 页面文案与 UI 组件优化

**目标状态**：
- 逐页审查并确定需要调整的文案与 UI 组件
- 清理装饰性噪音，确保展示与能力一致

**逐页改动清单（初稿）**：

**Landing（首页）**
- 去掉首页中心“PROJECT Goodman”装饰元素的边框与闪烁动效（当前代码未发现该组件，需确认运行态或样式来源）
- “为什么选择 Goodman？”区块背景改为与其他区块一致的白色（若运行态为深色需排查样式覆盖）
- 收敛装饰性动效（入场动画、悬浮高亮、过度阴影）与视觉噪音
- 收紧核心能力/卖点文案，避免“过度承诺”或模糊表述
- 统一中英文风格（主标题/副标题/标语的一致性）

**Login（登录页）**
- 将“登录后可访问完整功能”替换为“当前不开放用户注册/普通账号登录，仅提供管理员入口”
- 仅保留与实际权限模型一致的提示文案

**Chat（对话页）**
- 访客横幅需明确展示“每小时限额”的具体数值（消息/上传/提取），避免只说“有限额”
- 小屏幕与无配额数据时，仍需有可理解的限额提示或引导

**Documents（文档页）**
- 目前未发现明显文案问题，保持不变（后续实现阶段再复核）

**About（关于页）**
- 全文案重写，避免“重新定义财务工作流”等过强表述
- 移除“GPT-4o / Chain of Thought”等容易被视为不必要/不准确的内部细节
- “实时引用最新法规”等承诺需降级为更准确表述
- 版本信息（Current Version: V4.2.1）需改为真实版本或移除

**Help（帮助页）**
- 全文案重写，避免“几秒钟内完成”等时间承诺
- 明确哪些功能仅管理员可用、访客限制范围
- 说明需与实际功能一致（上下文记忆、自动调用工具、文档处理范围等）
- “联系技术支持”需确认实际支持渠道或改为更合适的引导

**Admin（管理页）**
- 目前未发现明显文案问题，保持不变（后续实现阶段再复核）

**验收标准**：
- [ ] 输出逐页改动清单（包含 Landing、Login、Chat、Documents、About、Help、Admin）
- [ ] 文案与功能能力一致（不夸大、不含糊）
- [ ] 视觉样式更统一（字体、间距、动效更克制）
