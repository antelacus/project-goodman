# v4.6 性能优化 - Phase 1 需求文档

## 概述

| 属性 | 详情 |
|------|------|
| **功能名称** | 性能优化 (Performance Optimization) |

| **依赖** | v4.4 生产就绪（staging + 观测能力） |
| **状态** | Phase 1 - 需求定义 |

---

## 问题陈述

当前项目在功能层面已覆盖核心场景，但仍存在"可用但不稳定"的问题：

1. **关键功能稳定性不足**：部分工作流偶发失败（Agent 检索、报告生成、提取流程）。
2. **性能不可控**：缺少端到端性能基线与明确的性能目标。
3. **回归风险**：缺乏系统化的回归验证，导致"修复一处、影响他处"的情况。
4. **功能说明与行为不一致**：部分工具/流程描述与实际行为存在偏差，影响可靠性。
5. **页面文案与视觉噪音**：存在装饰性过强或承诺不精准的展示，影响可信度。
6. **报告分析缺乏针对性**：财务报告仅基于通用基准分析，未结合公司特性（IDM 模式、行业特征、内部标准），导致分析结论泛化或误判。

v4.6 的目标是让“每个关键功能都能稳定工作”，并通过明确的成功率、错误率、性能指标进行量化验收。

---

## 范围

### 范围内

1. 定义"关键功能清单"与验收标准
2. 建立成功率/错误率/性能阈值（基于 staging 统计）
3. 关键路径稳定性优化（Agent 检索、报告生成、提取、Quick Actions、管理员流程）
4. 统一功能描述与行为（prompt/文案/工具说明）
5. 回归验证与自动化测试补齐
6. 页面文案与 UI 组件优化（逐页确定改动清单）
7. 报告生成上下文增强（注入公司档案与财务制度，提升分析针对性）

### 范围外

- 新增业务功能
- 大规模性能压测与容量规划
- 多区域部署与系统架构重构
- 数据备份/灾备体系

### REQ-A2: 成功率/错误率/性能基线

**基线阈值（方案 1）**：

- **成功率**：关键流程成功率 ≥ 98%
- **错误率**：5xx 错误率 ≤ 0.5%
- **性能（P95）**：
  - 非 AI 接口：< 1s
  - 聊天：首 token < 3s，整体 < 12s
  - 报告生成：< 60s
  - 文档提取：< 45s

**验收标准**：

- [ ] staging 统计口径明确（采样周期与样本量）
- [ ] 指标在 CI/日志中可被追踪
- [ ] 所有关键功能均可映射到上述指标

### REQ-F2: 报告生成上下文增强

**问题陈述**：

当前报告生成工作流能正确计算财务指标并生成分析文本，但分析缺乏"灵魂"：

- LLM 仅看到数字和通用行业基准，无法理解公司特定背景
- 例如：存货周转率 1.79 次（周转天数 ~200 天）会被误判为"库存积压风险"，但对于 IDM 模式 + 电信业务公司，这是正常水平
- 分析结论偏向通用化，缺乏针对性和实际参考价值

**目标状态**：

- 报告生成工作流在分析阶段注入公司档案与财务制度作为上下文
- LLM 能够结合公司特性（行业、商业模式、内部基准）进行有针对性的分析
- 分析结论更具参考价值，避免"泛泛而谈"或"误判正常现象"

**上下文文档**：

| 文档名称 | doc_type | 作用 |
|---------|----------|------|
| `公司详细档案.md` | `business_info` | 提供公司画像：IDM 模式特性、行业分类、历史营收轨迹、存货周转基准、竞对对标、风险与机遇节点、AI 推理示例 |
| `财务管理制度.md` | `policy` | 提供内部标准：收入确认规则、存货跌价政策、折旧策略、财务健康区间（毛利率 20-25%、存货周转 1.5-2.0x 等） |

**预期效果示例**：

| 场景 | 当前输出 | 增强后输出 |
|-----|---------|-----------|
| 存货周转率 1.79x | "周转天数约 204 天，远高于行业平均，建议关注库存积压风险" | "周转天数约 204 天，符合 IDM 模式 + 电信业务特性（基准 180-240 天），处于正常区间。需关注 12 个月以上库龄占比" |
| 毛利率 22% | "毛利率 22%，处于中等水平" | "毛利率 22%，处于公司目标区间（20-25%）。低于纯数通厂商（30%+），但符合 IDM 重资产模式特征" |
| ROE 10% | "ROE 10%，盈利能力一般" | "ROE 10%，低于 Fabless 竞对（20-25%），主要受资产周转率拖累（重资产 Fab）。但权益乘数低，财务风险小" |

**技术方案概要**：

1. 在 `gather-context` 节点增加对 `公司详细档案` 和 `财务管理制度` 的内容检索
2. 将检索到的上下文内容传递给 `analyze-sections` 节点
3. 在 section analysis prompt 中注入公司上下文，指导 LLM 结合公司特性分析

**验收标准**：

- [ ] `gather-context` 节点能检索并返回两份上下文文档的内容
- [ ] `analyze-sections` 节点的 LLM prompt 包含公司上下文
- [ ] 生成的报告分析能体现公司特性（IDM 模式、行业基准、内部标准）
- [ ] 不影响报告生成性能（P95 仍 < 60s）
- [ ] 上下文文档缺失时能优雅降级（仅记录警告，不阻断流程）
