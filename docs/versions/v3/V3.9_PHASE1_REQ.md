## 1. 概述

### 1.1 背景

V3 主体开发已于 2025-12-30 完成（V3.0-V3.7, V3.10）。在此期间进行了全面的代码审查，发现了若干安全漏洞和代码质量问题。

### 1.2 来源

本需求整合自三份独立的代码审查报告：

| 来源 | 审查方法 | 重点领域 |
|------|----------|----------|
| Antigravity AI | 静态代码分析 | 类型安全、硬编码、技术债务 |
| Claude Code | 多代理深度分析 | API层、组件层、数据库层、安全层、AI Agent |
| 手动审查 | 模式识别、架构评审 | 状态管理、测试基础设施、死代码 |

**综合报告**: `docs/code-review/COMBINED_CODE_REVIEW_2025_12_31.md`

### 1.3 动机

- **安全合规**: 修复可能导致数据泄露或攻击的安全漏洞
- **系统稳定性**: 消除可能导致运行时崩溃的代码问题
- **可维护性**: 提高代码质量，降低未来维护成本
- **专业形象**: 作为面向潜在雇主的演示项目，代码质量直接反映开发能力

## 2. 目标与范围

### 2.1 主要目标

1. **修复所有严重安全漏洞**（🔴 紧急级别）
2. **提升代码健壮性**（错误处理、类型安全）
3. **消除技术债务**（遗留代码、重复定义）
4. **改进系统可观测性**（日志安全、错误追踪）

### 2.2 范围内

| 类别 | 包含内容 |
|------|----------|
| **安全** | CSP 配置、CSRF 保护、敏感数据存储、时序攻击、日志泄露 |
| **AI Agent** | 消息转换、JSON 解析、类型安全、状态管理 |
| **API 层** | 错误处理统一、输入验证、响应格式 |
| **前端** | 类型共享、性能优化、样式规范 |
| **数据库** | 缺失字段、类型同步 |
| **架构** | 内存状态迁移到 Redis、遗留代码清理 |

### 2.3 范围外

| 排除项 | 原因 |
|--------|------|
| 新功能开发 | 属于 V3.8 或后续版本 |
| 测试框架迁移 (Vitest) | 工作量大，可独立规划 |
| UI 国际化 | 非紧急，可独立规划 |
| 文档解析递归逻辑 | 需要更深入的设计 |

## 3. 成功标准

### 3.1 安全指标

| 指标 | 当前状态 | 目标状态 |
|------|----------|----------|
| CSP `unsafe-*` 指令 | 存在 | 移除 |
| 客户端敏感数据存储 | localStorage/sessionStorage | 仅 HttpOnly cookies |
| CSRF 保护 | 无 | 所有状态变更端点 |
| 密码比较 | 非常量时间 | 常量时间 |
| 日志敏感信息 | 存在 | 零泄露 |

### 3.2 代码质量指标

| 指标 | 当前状态 | 目标状态 |
|------|----------|----------|
| `as any` 使用次数 | 15+ | < 5（必要情况） |
| 重复类型定义 | 存在 | 统一到共享文件 |
| API 错误处理 | 不一致 | 统一使用 `createErrorResponse()` |
| 内存状态管理 | Map 对象 | Redis |

### 3.3 功能指标

| 指标 | 当前状态 | 目标状态 |

| 临时文档清理 | 失效 (`is_temp` 缺失) | 正常工作 |
| 多轮工具调用 | 可能断裂 | 正确传递 tool_call_id |
| JSON 解析错误 | 崩溃 | 优雅降级 |

## 4. 详细需求

### 4.1 🔴 紧急级别（P0）

#### REQ-001: 移除 CSP 不安全指令

**当前问题**: `next.config.ts` 中使用 `'unsafe-inline'` 和 `'unsafe-eval'`，完全绕过 XSS 防护

**需求**:
- 移除 `script-src` 中的 `'unsafe-inline'` 和 `'unsafe-eval'`
- 使用 nonce 或 hash 方式允许必要的内联脚本
- 验证 Next.js 15 是否真正需要这些指令

**验收标准**: CSP 头不包含 `unsafe-*` 指令，应用正常运行

---

#### REQ-002: 移除客户端敏感数据存储

**当前问题**:
- `PasswordModal.tsx`: localStorage 存储 session token
- `documents/page.tsx`: sessionStorage 存储 adminPassword

**需求**:
- 移除所有 localStorage/sessionStorage 中的敏感数据存储
- 仅依赖 HttpOnly cookies 进行会话管理
- 审查并移除 `ADMIN_SESSION_KEY` 相关的客户端逻辑

**验收标准**: 浏览器开发者工具中 localStorage/sessionStorage 不包含任何 token 或密码

---

#### REQ-003: 统一使用 Redis 替代内存 Map

**当前问题**:
- `middleware.ts`: 使用 `rateLimitStore = new Map()`
- `admin-auth.ts`: 使用 `activeSessions = new Map()`
- 重启丢失状态，无法横向扩展

**需求**:
- 将所有内存 Map 状态迁移到 Redis
- 移除 `admin-auth.ts` 中的遗留内存认证代码
- 确保只有一套认证系统（Redis 版本）

**验收标准**: 代码中不存在用于状态管理的 `new Map()` 调用

---

#### REQ-004: 修复 is_temp 字段缺失

**当前问题**: `20250113000003.sql` 中的清理函数引用 `is_temp` 字段，但该字段从未创建

**需求**:
- 添加迁移创建 `documents.is_temp BOOLEAN DEFAULT false` 列
- 或修改清理逻辑使用现有的 `expires_at` 字段（V3.10 已添加）

**验收标准**: pg_cron 临时文档清理任务正常执行

---

#### REQ-005: 修复 AI Agent 消息转换

**当前问题**: `agent-loop.ts` 中 ToolMessage 转换丢失 `tool_call_id`

```typescript
// 当前：丢失元数据
return { role, content: msg.content } as any;
```

**需求**:
- 正确映射 ToolMessage: `{ role: "tool", tool_call_id, content }`
- 保留所有必要的消息元数据
- 移除 `as any` 类型断言

**验收标准**: 多轮工具调用链正常工作，可验证通过连续调用多个工具的场景

---

#### REQ-006: 添加 JSON.parse 错误处理

**当前问题**: `agent-loop.ts:93` 无 try-catch，畸形参数导致崩溃

**需求**:
```typescript
try {
    return { id: tc.id, name: tc.function.name, arguments: JSON.parse(tc.function.arguments) };
} catch (e) {
    console.warn(`Failed to parse arguments for ${tc.function.name}`);
    return { id: tc.id, name: tc.function.name, arguments: {} };
}
```

**验收标准**: 畸形 JSON 参数不会导致工作流崩溃，而是优雅降级

### 4.2 🟠 高优先级（P1）

#### REQ-007: 添加 CSRF Token 验证

**受影响端点**:
- POST `/api/auth/login`
- POST `/api/admin/verify-password`
- POST `/api/documents/upload-temp`
- PATCH `/api/documents`
- DELETE `/api/documents`

**需求**:
- 实现 CSRF token 生成和验证机制
- 所有状态变更端点要求有效的 CSRF token
- 考虑使用 Double Submit Cookie 模式

**验收标准**: 无有效 CSRF token 的请求返回 403

---

#### REQ-008: 更新数据库类型定义

**当前问题**: `src/lib/database/types.ts` 缺失 V3.10 添加的字段

**需求**:
- 运行 `npx supabase gen types typescript` 生成最新类型
- 或手动添加缺失的字段定义
- 移除 RPC 调用处的 `as any` 类型断言

**验收标准**: TypeScript 编译无类型错误，IDE 能正确提示所有字段

---

#### REQ-009: 统一 API 错误处理

**当前问题**: 部分路由使用 `createErrorResponse()`，部分直接返回 `NextResponse.json()`

**需求**:
- 所有 API 路由统一使用 `createErrorResponse()` 函数
- 确保生产环境不暴露 `error.message` 详情
- 添加请求 ID 追踪

**验收标准**: 所有 API 错误响应格式一致，包含 requestId

---

#### REQ-010: 添加缺失的 Zod 验证

**受影响端点**:
- `/api/chat/route.ts` - 无消息长度限制
- `/api/quick-actions/extract/route.ts` - 无请求结构验证

**需求**:
- 为所有端点添加 Zod schema
- 添加合理的长度限制（如消息最大 10000 字符）
- 使用 `api-schemas.ts` 中的验证模式

**验收标准**: 超长输入返回 400 错误，而非处理失败

---

#### REQ-011: 提取共享 Message 类型

**当前问题**: `ChatWorkspace.tsx` 和 `MessageList.tsx` 重复定义 Message 接口

**需求**:
- 创建 `src/types/message.ts` 共享类型文件
- 所有组件引用共享类型
- 与 API 响应类型保持一致

**验收标准**: 代码中只有一处 Message 类型定义

---

#### REQ-012: 清理遗留认证代码

**当前问题**: `admin-auth.ts` 包含并行的内存认证系统和 Redis 认证系统

**需求**:
- 删除所有内存版本的认证函数
- 确保只使用 Redis 版本
- 移除相关的 DEBUG 日志

**验收标准**: `admin-auth.ts` 中无 `new Map()` 或内存状态管理代码

---

#### REQ-012b: Service Role Key 隔离

**当前问题**: `src/lib/documents/storage.ts` 中的 `createStorageClient` 使用 Service Role Key，如果被客户端组件意外导入会造成安全风险

**需求**:
- 在文件顶部添加 `'use server'` 指令或明确的服务端限制注释
- 考虑添加 ESLint 规则防止该模块被 Client Components 导入
- 审查所有 Service Role Key 使用点，确保仅在服务端调用

**验收标准**:
- 文件包含明确的服务端限制标记
- 无客户端组件导入该模块

## 5. 依赖与风险

### 5.1 依赖

| 依赖项 | 说明 |
|--------|------|
| V3.10 用户管理系统 | 已完成，提供了认证基础设施 |
| Redis | 已部署，用于状态存储 |
| 现有测试 | 需要验证修复不破坏现有功能 |

### 5.2 风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| CSP 修改导致功能异常 | 高 | 逐步测试，保留回退方案 |
| 认证代码清理影响现有会话 | 中 | 在低峰期部署，准备回滚 |
| 类型修复引入编译错误 | 低 | 增量修复，持续集成验证 |

### 5.3 实施建议

1. **分批实施**: 按优先级分批修复，每批完成后部署验证
2. **紧急优先**: 先修复 P0 级别的安全问题
3. **测试覆盖**: 每个修复都应有对应的手动测试验证
4. **文档更新**: 修复完成后更新 TRACK
