## 1. Executive Summary

### 1.1 Purpose

本文档定义 V3.1 LangGraph 预备重构的技术需求。这是一次内部重构，用户不会感知到变化，但为后续 V3.3 (智能文档系统) 和 V3.4 (LangGraph 完整迁移) 奠定基础。

### 1.2 Background

V3.0 VPS 迁移已完成 (2025-12-12)。根据 V3_DEVELOPMENT_PLAN.md 中的架构决策，我们选择采用 LangGraph 作为 Agent 编排框架。在正式引入 LangGraph 之前，需要重构现有代码以：

1. 使现有架构更接近 LangGraph 的模式
2. 减少迁移时的代码变更量
3. 降低迁移风险

### 1.3 Scope

**In Scope**:

- 代码重构（不改变功能行为）
- 类型整合和标准化
- 步骤函数提取
- 工具定义集中化
- 错误类型层次创建

**Out of Scope**:

- 添加 LangGraph 依赖（V3.4）
- 实现 WebSocket 流式传输（V3.3+）
- 新功能开发
- 数据库 schema 变更
- UI/UX 变更

## 2. Current State Analysis

### 2.1 Codebase Overview

| Component | Files | Lines | Location |
|-----------|-------|-------|----------|
| API Routes | 14 | ~2,573 | `src/app/api/` |
| Core Libraries | 8 | ~1,500 | `src/lib/` |
| Type Definitions | Scattered | ~500 | Multiple locations |
| Financial Functions | 1 | ~1,000 | `src/lib/preset-functions.ts` |

### 2.2 Identified Pain Points

#### 2.2.1 Types Scattered Across Files

当前类型定义分散在多个位置：

| Location | Types Defined |
|----------|---------------|
| `src/app/api/*/route.ts` | Request/Response interfaces (每个路由重复定义) |
| `src/lib/database.types.ts` | Supabase 自动生成类型 |
| `src/lib/preset-functions.ts` | `PresetFunction`, `CalculationResult` |
| `src/lib/structured-extraction.ts` | `DocumentType`, `ExtractionResult` |
| `src/lib/confidence-scoring.ts` | `ConfidenceMetric`, `ConfidenceScore` |
| `src/store/documents.ts` | Frontend state types |

**问题**:

- 相同类型在多处重复定义
- 修改类型时需要同步多个文件
- 难以追踪类型依赖关系

#### 2.2.2 No Tool Abstraction Layer

当前"工具"分散在多个库文件中，没有统一接口：

```
当前结构:
src/lib/
├── preset-functions.ts      # 22 个财务计算函数
├── structured-extraction.ts # 数据提取函数
├── confidence-scoring.ts    # 置信度计算
├── storage-helpers.ts       # 存储操作
└── (others)                 # 各种辅助函数
```

**问题**:

- 无统一工具接口，难以注册到 LangGraph ToolNode
- 工具元数据（描述、输入输出schema）与实现代码耦合
- 难以添加工具调用日志、重试逻辑等横切关注点

#### 2.2.3 Routes Contain Implicit Workflows

API 路由包含隐式多步骤工作流，以 `financial-analysis` 为例：

```
步骤 1: 构建函数定义 →
步骤 2: 调用 OpenAI →
步骤 3: 解析工具调用 →
步骤 4: 查询财务数据 →
步骤 5: 执行计算 →
步骤 6: 评估置信度 →
步骤 7: 生成响应
```

**问题**:

- 步骤逻辑与请求处理代码耦合
- 无法复用步骤（如"评估置信度"在多个路由中重复）
- 难以添加分支、重试、错误恢复逻辑
- 无法可视化工作流程

#### 2.2.4 No Explicit State Definition

每个请求都是无状态的，工作流状态隐含在局部变量中：

```typescript
// 当前模式：隐式状态
export async function POST(request: Request) {
  const body = await request.json();          // 输入
  const functionDefs = buildFunctionDefs();   // 中间状态
  const openaiResponse = await callOpenAI();  // 中间状态
  const toolResult = executeFunction();       // 中间状态
  const confidence = calculateConfidence();   // 中间状态
  return Response.json({ ... });              // 输出
}
```

**问题**:

- 状态类型不明确，难以追踪数据流
- 无法持久化中间状态（用于重试、调试）
- 与 LangGraph StateGraph 模式不兼容

## 3. Target Architecture

### 3.1 Design Goals

| Goal | Rationale |
|------|-----------|
| **类型集中化** | 单一位置管理所有工作流相关类型 |
| **步骤函数化** | 每个工作流步骤是独立的纯函数 |
| **工具标准化** | 统一工具接口，便于 LangGraph 集成 |
| **状态显式化** | 明确定义工作流状态结构 |
| **向后兼容** | 重构不改变 API 行为 |

## 4. Technical Requirements

### 4.1 Phase A: Extract Explicit State Types (关键)

**Objective**: 为每个主要工作流创建显式状态类型定义。

**Deliverables**:

1. **`src/lib/types/workflow-states.ts`**

```typescript
// 财务分析工作流状态
export interface FinancialAnalysisState {
  // 输入
  input: {
    question: string;
    documentId?: string;
    uploadedDocument?: { text: string; fileName: string };
  };

  // 中间状态
  routing: {
    selectedFunction: string | null;
    confidence: number;
  };

  dataQuery: {
    availableMetrics: string[];
    missingMetrics: string[];
    queryResults: Record<string, number>;
  };

  calculation: {
    result: number | null;
    formula: string;
    inputs: Record<string, number>;
  };

  confidence: {
    score: number;
    factors: ConfidenceFactor[];
    threshold: number;
    passed: boolean;
  };

  // 输出
  output: {
    answer: string;
    calculation?: CalculationResult;
    citations?: Citation[];
    warnings?: string[];
  };

  // 元数据
  meta: {
    startTime: number;
    currentStep: string;
    errors: WorkflowError[];
  };
}

// 合规指导工作流状态
export interface GuidanceChatState {
  input: { ... };
  search: { ... };
  reasoning: { ... };
  confidence: { ... };
  output: { ... };
  meta: { ... };
}
```

**Acceptance Criteria**:

- [ ] 每个主要工作流（financial-analysis, guidance-chat, landing-chat）有对应的状态类型
- [ ] 状态类型包含：input, 中间步骤状态, output, meta
- [ ] 现有路由代码可以逐步迁移到使用这些类型
- [ ] 类型导出从 `src/lib/types/index.ts`

### 4.2 Phase B: Extract Step Functions (高优先级)

**Objective**: 将路由处理器中的隐式步骤提取为独立的纯函数。

**Deliverables**:

1. **`src/lib/workflows/financial-analysis/steps.ts`**

```typescript
// 步骤 1: 路由问题到函数
export async function routeToFunction(
  state: FinancialAnalysisState
): Promise<FinancialAnalysisState> {
  // 纯函数：接收状态，返回更新后的状态
  const { question } = state.input;
  const selectedFunction = await determineFunction(question);

  return {
    ...state,
    routing: {
      selectedFunction,
      confidence: selectedFunction ? 0.8 : 0.2,
    },
    meta: {
      ...state.meta,
      currentStep: 'route_to_function',
    },
  };
}

// 步骤 2: 查询数据
export async function queryData(
  state: FinancialAnalysisState
): Promise<FinancialAnalysisState> { ... }

// 步骤 3: 执行计算
export async function executeCalculation(
  state: FinancialAnalysisState
): Promise<FinancialAnalysisState> { ... }

// 步骤 4: 评估置信度
export async function evaluateConfidence(
  state: FinancialAnalysisState
): Promise<FinancialAnalysisState> { ... }

// 步骤 5: 生成响应
export async function generateResponse(
  state: FinancialAnalysisState
): Promise<FinancialAnalysisState> { ... }
```

**Step Function Contract**:

```typescript
type StepFunction<S> = (state: S) => Promise<S>;
```

**Acceptance Criteria**:

- [ ] 每个步骤是纯函数（输入状态 → 输出状态）
- [ ] 步骤函数不直接访问 Request/Response 对象
- [ ] 步骤函数可独立测试
- [ ] 原路由简化为：初始化状态 → 顺序调用步骤函数 → 返回响应

### 4.3 Phase C: Centralize Tool Definitions (中优先级)

**Objective**: 创建统一的工具接口和注册表。

**Deliverables**:

1. **`src/lib/tools/registry.ts`**

```typescript
// 统一工具接口
export interface Tool<TInput, TOutput> {
  name: string;
  description: string;
  category: ToolCategory;

  // Schema 定义（用于 LangGraph ToolNode）
  inputSchema: z.ZodSchema<TInput>;
  outputSchema: z.ZodSchema<TOutput>;

  // 执行函数
  execute: (input: TInput) => Promise<TOutput>;

  // 元数据
  metadata?: {
    timeout?: number;
    retryable?: boolean;
    requiresAuth?: boolean;
  };
}

// 工具注册表
class ToolRegistry {
  private tools: Map<string, Tool<unknown, unknown>> = new Map();

  register<TInput, TOutput>(tool: Tool<TInput, TOutput>): void { ... }
  get(name: string): Tool<unknown, unknown> | undefined { ... }
  getByCategory(category: ToolCategory): Tool<unknown, unknown>[] { ... }
  toOpenAIFunctionDefs(): OpenAIFunctionDef[] { ... }
  toLangGraphTools(): LangGraphTool[] { ... }  // 为 V3.4 预留
}

export const toolRegistry = new ToolRegistry();
```

1. **`src/lib/tools/financial-tools.ts`**

```typescript
// 将 preset-functions.ts 中的函数封装为 Tool 接口
import { toolRegistry, Tool } from './registry';
import { presetFunctions } from '../preset-functions';

// 为每个 preset function 创建 Tool wrapper
presetFunctions.forEach(fn => {
  toolRegistry.register({
    name: fn.name,
    description: fn.interpretation,
    category: 'financial',
    inputSchema: z.object(
      fn.requiredInputs.reduce((acc, input) => ({
        ...acc,
        [input]: z.number(),
      }), {})
    ),
    outputSchema: z.object({
      value: z.number(),
      formula: z.string(),
      unit: z.string(),
    }),
    execute: async (input) => fn.calculate(input),
  });
});
```

**Acceptance Criteria**:

- [ ] 所有现有工具（财务计算、搜索、提取）有统一接口
- [ ] 工具注册表支持按类别查询
- [ ] 可导出为 OpenAI function definitions
- [ ] 预留 LangGraph ToolNode 转换接口
- [ ] 现有代码可通过注册表调用工具

### 4.5 Phase E: Create Error Type Hierarchy (低优先级)

**Objective**: 创建结构化的错误类型，为 LangGraph 条件边错误处理做准备。

**Deliverables**:

1. **`src/lib/errors/base-error.ts`**

```typescript
export abstract class WorkflowError extends Error {
  abstract readonly code: string;
  abstract readonly recoverable: boolean;

  constructor(
    message: string,
    public readonly context?: Record<string, unknown>
  ) {
    super(message);
    this.name = this.constructor.name;
  }

  toJSON() {
    return {
      name: this.name,
      code: this.code,
      message: this.message,
      recoverable: this.recoverable,
      context: this.context,
    };
  }
}
```

1. **`src/lib/errors/tool-errors.ts`**

```typescript
// 工具执行错误
export class ToolExecutionError extends WorkflowError {
  readonly code = 'TOOL_EXECUTION_ERROR';
  readonly recoverable = true;

  constructor(
    public readonly toolName: string,
    message: string,
    context?: Record<string, unknown>
  ) {
    super(`Tool '${toolName}' failed: ${message}`, context);
  }
}

export class ToolNotFoundError extends WorkflowError {
  readonly code = 'TOOL_NOT_FOUND';
  readonly recoverable = false;
}

export class ToolInputValidationError extends WorkflowError {
  readonly code = 'TOOL_INPUT_VALIDATION';
  readonly recoverable = false;
}
```

1. **`src/lib/errors/workflow-errors.ts`**

```typescript
// 工作流错误
export class InsufficientDataError extends WorkflowError {
  readonly code = 'INSUFFICIENT_DATA';
  readonly recoverable = true;  // 可尝试其他数据源
}

export class LowConfidenceError extends WorkflowError {
  readonly code = 'LOW_CONFIDENCE';
```

**Acceptance Criteria**:

- [ ] 错误基类包含 `code`, `recoverable`, `context` 属性
- [ ] 工具错误和工作流错误分类清晰
- [ ] `recoverable` 属性指导未来的重试逻辑
- [ ] 错误可序列化为 JSON（用于 API 响应）

## 5. Implementation Constraints

### 5.1 Backward Compatibility

- **API 接口不变**: 所有现有 API 端点的请求/响应格式保持不变
- **渐进式迁移**: 可以逐个路由迁移，不需要一次性全部完成
- **测试验证**: 每个重构步骤后，现有功能应正常工作

### 5.2 Code Quality

- **类型安全**: 所有新代码必须有完整的 TypeScript 类型
- **无新依赖**: Phase A-E 不引入新的 npm 依赖
- **文档**: 遵循 CLAUDE.md 中的代码文档标准（注释解释"why"，不注释显而易见的"what"）

### 5.3 Testing Strategy

- **单元测试**: 步骤函数应可独立单元测试
- **集成测试**: API 端点行为应与重构前一致
- **手动测试**: 每个工作流在实际环境中验证

| Risk | Impact | Mitigation |
|------|--------|------------|
| 重构引入 regression | High | 每个 Phase 后进行完整功能测试 |

## 9. Open Questions

1. **步骤函数的错误处理策略**: 是在步骤内部 try-catch，还是让错误冒泡到工作流层？
   - **建议**: 让错误冒泡，由工作流层统一处理，这更符合 LangGraph 的条件边模式

2. **状态持久化**: 是否需要在本阶段添加状态持久化（如 Redis）？
   - **建议**: 不需要，V3.1 保持内存状态，V3.4 再考虑持久化

3. **工具注册时机**: 工具是在应用启动时注册，还是按需注册？
   - **建议**: 应用启动时注册所有工具，保持简单
