# 事故响应手册（Incident Runbook）

本文档用于生产环境事故响应与回滚指导，适用于演示与真实运行场景。

## 1. 目标与范围

- 快速定位故障原因并恢复服务
- 保证核心接口 `/api/health` 可用
- 形成可复盘、可再现的处理流程

---

## 2. 事故分级

| 等级 | 定义 | 目标响应时间 |
|------|------|---------------|
| **Critical** | 系统不可用、数据丢失或安全事件 | 立即响应 |
| **High** | 核心功能失效，影响主要用户 | 同日修复 |
| **Medium** | 功能降级，有替代方案 | 下一个可用窗口 |
| **Low** | 轻微问题或体验瑕疵 | 迭代修复 |

---

## 3. 响应流程

### 3.1 发现与确认

1. 监控告警触发（UptimeRobot/日志）
2. 确认 `/api/health` 状态
3. 记录触发时间、影响范围与初步症状

### 3.2 临时缓解

1. 若为新版本引起，优先回滚
2. 关闭高风险功能或降级非核心功能
3. 保证核心路径可用（登录、对话、报告）

### 3.3 根因定位

1. 查看应用日志：`docker logs -f goodman`
2. 查看 Redis/Supabase 状态
3. 查看 Sentry 错误堆栈与 requestId

### 3.4 恢复与验证

1. 修复或回滚后重新部署
2. 通过健康检查与冒烟测试
3. 监控 30-60 分钟稳定性

### 3.5 复盘与记录

1. 记录根因与处理步骤
2. 更新 `CHANGELOG.md` 与相关文档
3. 如涉及流程缺口，更新本手册

---

## 4. 回滚流程

### 4.1 应用回滚

1. 切回上一个稳定版本
2. 重新构建并启动容器
3. 验证 `/api/health`

参考命令（详见 `docs/DEPLOYMENT_CHECKLIST.md`）：

```bash
# 回滚到上一个提交
git checkout HEAD~1
cd /home/deploy/goodman && docker compose up -d --build goodman
```

### 4.2 数据回滚

- Supabase 迁移为前向，不建议直接回滚
- 重大变更需提前备份与演练

---

## 5. 常见故障排查

### 5.1 健康检查失败

- 检查容器状态：`docker ps --filter "name=goodman"`
- 检查日志：`docker logs goodman`
- 检查端口占用与反向代理配置

### 5.2 Redis 连接异常

- 检查 Redis 容器状态与密码配置
- 查看应用日志中 Redis 连接错误

### 5.3 Supabase 访问异常

- 检查 Supabase Dashboard 状态
- 验证 `NEXT_PUBLIC_SUPABASE_URL` 与 key 是否正确

### 5.4 错误追踪飙升

- 查看 Sentry 错误分布与版本
- 关联 requestId 查找具体 API route
